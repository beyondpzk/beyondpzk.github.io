# 室内巡逻执行流程：从示教建图到局部绕障

> **核心思路**：先示教并建立关键帧地图，再由定位层选择子目标、局部策略提出轨迹、独立安全层检查后执行。本文描述的是待验证的组合方案。
>
> 定位层告诉机器人"我在哪、下一站去哪"，VLA 负责"怎么走过去（绕开障碍）"。

---

## 全景：两步走

```
═══════════════════════════════════════════════════════════
Step 1（首次部署或地图更新）  示教建图：人牵机器人走一圈
═══════════════════════════════════════════════════════════
     产出：轻地图 = 一串编号关键帧 + 每帧特征 + 帧间距离
                        ↓
═══════════════════════════════════════════════════════════
Step 2（地图有效期间）      自主巡逻：沿地图走 + 实时避障
═══════════════════════════════════════════════════════════
     输入：轻地图      输出：走完路线，途中自动绕开障碍
```

---

## Step 1：示教建图（人牵着走一圈）

```
人牵着机器人沿巡逻路线走一圈（正常步速，转弯放慢）
        │
        ▼
① 机载程序自动记录图像流（30fps 全量落盘）+ 里程计
        │
        ▼
② 走完后跑一个脚本，全自动完成建图：
   ├─ DINOv3 自动挑关键帧（直路稀疏约 1 帧/米，转弯自动加密）
   ├─ CosPlace 给每个关键帧算 512 维特征（"检索指纹"）
   ├─ 里程计算相邻关键帧的真实间距
   └─ （可选）VLM 给关键帧打语义标签："走廊""电梯厅""前台"
        │
        ▼
产出轻地图（整个楼道通常只有几 MB~几十 MB）：

topomap/
├── 0.png  1.png  ...  N.png      ← 关键帧，编号即路线顺序
├── global-feats-cosplace.h5      ← 每帧的检索指纹
└── meta.json                     ← 相邻帧间距（米）
```

操作流程可以收敛为示教与建图两步，但部署前仍需完成相机与机体外参标定、时间同步和参数验证。图像目标策略可减少米制接口的工作量。

---

## Step 2：自主巡逻（沿路线走 + 实时避障）

### 启动

启动时先在关键帧库中全局检索，再通过多帧一致性确认位置和方向。只有达到定位置信条件才开始运动；相似走廊或反向视角可能需要额外观测或人工确认。

### 每一帧干什么（巡逻主循环，每秒约 5 次）

```
相机来一帧
   │
   ▼
┌─────────────────────────────────────────────┐
│ A. 定位：我在路线哪？                         │
│    当前画面 vs 地图指纹库 → 最像第 k 帧       │
│    （时序滤波降低跳错概率）            │
└─────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────┐
│ B. 定目标：下一站去哪？                       │
│    目标 = 第 k+1 个关键帧                     │
│    Reloc3r 估计方向，并结合       │
│    可靠尺度观测 → 机体系点目标 (x, y)       │
└─────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────┐
│ C. 执行：怎么走过去？（VLA 上场）             │
│    VLA 执行器：当前画面 + 目标                  │
│      · 点目标 (x, y) → PointNav 模型          │
│      · 或直接给子目标关键帧 → 图像目标模型      │
│        → 候选轨迹，再经几何安全检查                   │
│    ★ 避障就发生在这里：                      │
│      走廊有人/有箱子 → 提出局部绕行轨迹           │
│      （原版 GuideNav 没有专用避障模块）   │
└─────────────────────────────────────────────┘
   │
   ▼
D. 到站判断：定位显示我越过了第 k+1 帧？
   ├─ 否 → 回到 A，继续朝它走
   └─ 是 → 目标切换到第 k+2 帧，回到 A
   │
   ▼
到达最后一帧 → 停车并结束当前路线
反向或环线巡逻需另建有效路线连接、方向观测与调度逻辑
```

### 避障为什么能"绕完自动回路线"

这是这套组合的关键机制：**避障是局部的，路线是全局拉住的**。

```
巡逻路线（关键帧链）  ●━━━●━━━●━━━●━━━●
                        ↓ 障碍出现
                      ●━━━● ╭──╮ ●━━━●
                           ╲障碍╱ ← VLA 局部绕行，航点偏出路线
                            ╲__╱
                              │
   绕行期间：定位层每帧仍在比对"我像哪一帧"
   → 一旦绕过障碍，目标自然指回下一个关键帧
   → 机器人被"拉回"路线，继续巡逻
```

局部策略能否绕障取决于训练数据、观测和部署场景。绕行后回归路线也依赖视觉共视和定位置信度；偏离过大时应停止并重定位，不能假设定位始终有效。

### 异常处理（巡逻中出问题怎么办）

| 情况 | 系统反应 |
|---|---|
| 眼前纹理太少/画面失败 | 定位低置信时停车；只有局部几何和短时里程计均可信才允许受限低速恢复 |
| 定位"找不到自己"了 | 确认旋转空间安全后多视角检索；超时仍未确认则停车并请求接管 |
| 障碍堵死过不去（如关门） | 等待 N 秒 → 标记该段"Blocked"写入地图 → 报告/返程 |
| VLA 异常 | 仅在定位可信且路径安全时低速回退，否则停车 |

## 和原版 GuideNav 的差别（为什么加 VLA）

| | 原版 GuideNav | 本方案 |
|---|---|---|
| 沿路线走 | ✅ | ✅ |
| 遇到障碍 | ❌ 无专用障碍检测与避障模块 | 候选绕行轨迹 + 安全检查 + 重定位验证 |
| 动作平滑度 | 一般（先转后走） | 可输出连续轨迹，需测量运动质量 |
| 终点只能是路线末端 | ✅ | ✅ 且支持语义目标（"去前台"，需打标） |
| 新增成本 | — | 多跑一个 VLA 模型（Orin NX 可跑 19M~306M 小模型；Thor 可跑 4B） |

## 部署清单

**硬件**：Unitree Go2（或同级四足/轮式底盘）+ RealSense D435i（只用 RGB）+ Jetson Orin NX / Thor。

**软件模块**（按改动量排序）：

1. GuideNav 原版代码 —— 定位与建图，复用核心组件，按接口调整；
2. 扩展示教元数据 —— 从里程计记录帧间距，写 `meta.json`；
3. 新增目标接口桥 —— 融合方向、尺度与坐标变换，输出机体系点目标；
4. VLA 执行器 —— 选现成开源模型，优先验证已有权重，必要时适配或微调（见下方选型）；
5. 航点跟踪 + 安全急停 —— 底盘侧常规件。

### 执行器模型选型（按调研记录，实际以官方最新发布为准）

| 模型 | 权重 | 接口 | 规格 | 备注 |
|---|---|---|---|---|
| **NoMaD / ViNT**（Berkeley） | ✅ 开源 checkpoint（[robodhruv/visualnav-transformer](https://github.com/robodhruv/visualnav-transformer)） | **图像目标**（子目标关键帧直接当 goal） | 19M~31M，Orin NX 可跑 | **默认推荐**；还自带拓扑图部署脚本 |
| **InternVLA-N1**（上海 AI Lab） | ✅ 开源（[HuggingFace](https://huggingface.co/InternRobotics/InternVLA-N1)） | 双系统（latent/pixel goal） | 需较强算力 | ⚠️ **CC BY-NC-SA 非商用许可**；代码 [InternNav](https://github.com/InternRobotics/InternNav) |
| **Qwen-RobotNav-4B** | ❌ **官方明确不开放权重**（[repo 声明](https://github.com/QwenLM/Qwen-RobotNav)："no plan to release the model weights"） | 点目标 PointNav | 4B，Thor | 想走 PointNav 接口需按其配方自训（Qwen3-VL + 4 层 MLP 动作头，成本约 2,816 H100 小时） |

**选型建议**：

- **默认走 NoMaD 图像目标接口**：子目标关键帧本身就是现成的 goal image，连 Reloc3r 接口桥都可以省掉（Reloc3r 退居到站判据的辅信号），是零训练、最低风险路径；
- 坚持 PointNav 接口（点目标）的场景（如要接自训 Qwen3-VL 动作头或其他坐标原生模型），接口桥才有存在必要；
- 商用项目注意 InternVLA-N1 的非商用许可限制。

**示例验收目标（非实测结果）**：

以下阈值用于说明验收方式；实际应同时约定路线长度、障碍类型、重复次数和允许的人工干预。

- 示教一次后，巡逻一圈成功率 ≥ 95%；
- 走廊中间放箱子/站人，能绕行并回到路线；
- 断电重启后放在路线任意位置，10 秒内自动找回位置继续巡逻。

## 附：关键帧间距（帧间距）怎么算出来

帧间距来自 **teach 时同步记录的里程计**——就是 Step 1 里"记录图像流 + 里程计"那一路数据的用途。

### 来源：teach 阶段的 `odom.csv`

示教记录时，除图像外，机器人持续输出里程计（Go2 腿部里程计 / RealSense visual odometry topic 均可），落成一张表：

```
odom.csv:  timestamp, pos_x, pos_y, pos_z, ori_x, ori_y, ori_z, ori_w, ...
```

### 计算：关键帧时间戳 → 路径弧长积分

选帧完成后，需要保留关键帧编号与原始时间戳的映射。对相邻两个关键帧：

```
1. 用关键帧 i 和 i+1 的时间戳，在 odom.csv 里插值出两个时刻的位姿
2. 把这两个时刻之间的所有里程计采样点做路径长度积分：
   d_i = Σ ‖p_{t+1} − p_t‖      （逐小段累加，不是两点直线距离）
3. d_i 即关键帧 i → i+1 的间距，写进 meta.json 的 spacing 数组
```

伪代码：

```python
odom = load_csv("odom.csv")                    # 按时间排序的位姿序列
for i in range(N):                             # N+1 个关键帧
    t0, t1 = keyframe_ts[i], keyframe_ts[i+1]  # 从编号—时间戳映射读取
    segment = odom.between(t0, t1)             # 两时刻间的里程计采样
    spacing[i] = sum(norm(p[j+1] - p[j]) for j in segment)
```

注意是**沿轨迹的弧长积分**而不是起终点直线距离——转弯段两者差很多，而转弯恰恰是关键帧最密的地方。

### 帧间距只提供尺度先验

示教时相邻关键帧的轨迹弧长，不等于 Repeat 时机器人到目标的直线距离。转弯、偏离路线和绕障都会放大两者差异，因此不能直接将弧长乘以 Reloc3r 单位方向作为精确米制目标。

可在共视充分的短直线路段验证标称间距近似；更一般的情况需要同步里程计、带标定的深度或多帧几何约束。普通单目相对深度不能直接提供绝对米制尺度。

如果缺少可靠尺度，优先验证图像目标接口。按固定距离选帧的构图器本身也需要位移估计，不能作为“没有里程计”的替代方案。

## 附：到站判断靠什么 —— VPR 为主，不用室内绝对定位

### 本质：拓扑事件，不是度量事件

"到达第 k+1 帧"不是坐标判断（"我到了 x=3.2m 处"），而是**拓扑判断**（"我看到的画面已经越过第 k+1 帧那个位置"）。三个信号按优先级融合：

| 信号 | 性质 | 角色 |
|---|---|---|
| **VPR 信念推进**（CosPlace + Markov 滤波） | 纯视觉 | **主判据**：belief 的 argmax 越过第 k+1 帧 → 判定到达 |
| Reloc3r 相对位姿 `x < 0`（子目标已到身后） | 纯视觉 | 辅判据：主判据的交叉验证 |
| 里程计剩余距离 < 阈值 | 度量，会漂移 | 仅作 sanity check，永不单独决策 |

VPR 可将当前观测重新锚定到示教记忆，避免仅靠里程计积分。但感知混叠仍可能产生错误跳转，因此推进判据应结合多帧一致性、相对方向和剩余距离检查。

### 为什么不用室内绝对定位

- **GPS**：室内没有；
- **UWB**：精度 0.3~1m 但需预装锚点基站——违背"开箱即用"，每个新场地都要施工；
- **WiFi RTT / 蓝牙**：精度米级且多径严重；
- **纯 IMU 推算**：几秒就漂。

VT&R 范式存在的意义就是**用视觉记忆检索替代绝对定位**——不问"我在哪米"，只问"我像哪一帧"。

### 室内 VPR 的退化场景与对策

| 退化场景 | 风险 | 对策 |
|---|---|---|
| **走廊/隔间长得一样**（感知混叠） | 检索跳错帧 | Markov 时序滤波压制（单帧跳变被信念平滑）+ 混叠段自动加密关键帧 |
| **大白墙弱纹理** | 描述符无区分度 | DINOv3 特征远强于手工特征；50 帧强制采样保底；实在不行墙上贴标识物（一张 A4 纸的成本） |
| **白天示教晚上巡逻** | 外观剧变检索失败 | CosPlace 本就跨光照训练，实测最稳的组件；极端场景示教两版（早/晚）或开补光 |

### 到站判据的验证

`lookahead` 与相对方向检查可以缓解部分相邻帧误差，但不能保证室内定位始终落在 ±1 帧。测试应覆盖相似走廊、岔路、反向启动和光照变化，并记录错误推进与终点误判。
