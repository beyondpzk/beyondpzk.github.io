# GuideNav 用于园区巡检：能力边界与系统设计

视觉示教复走与园区巡检共享一个特点：路线经常重复。但巡检还要求机器人独立处理障碍、执行到点任务，并长期维护地图。本文围绕这些差异，讨论如何将 GuideNav 扩展为分层巡检系统。

本文是基于公开论文与代码的方案分析，所列速度、频率和阶段目标均需在目标平台验证，不代表已完成的部署结果。

## 1. 能力边界(先对齐认知)

| 能力 | 现状 |
|---|---|
| 固定单链路线复走 | ✅ 直接可用(VT&R 甜区,巡检路线正是固定重复) |
| 单目低成本、地图可编辑可拼接 | ✅ 直接可用(1km≈24MB) |
| 光照/季节变化鲁棒 | ✅ Reloc3r 强项(夜间除外) |
| 避障/动态障碍 | ❌ 零避障 |
| 检查点/到点动作 | ❌ 无 |
| 异常检测 | ❌ 无(而这才是巡检的业务核心) |
| 多路线/目标选择 | ❌ 只有"走到最后一帧"一个目标 |
| 环线/回路 | ⚠️ 单链不支持 |
| 速度 | ⚠️ 0.15m/s 需提速验证 |
| 夜间/雨雾 | ⚠️ 纯 RGB 硬伤 |
| 报告定位 | ⚠️ 拓扑够用,度量需补 |
| 地图更新 | ⚠️ 需设计(见议题四) |

## 2. 系统设计原则

设计可以围绕三个目标展开：

1. **开箱即用** — 不建全局 SLAM、不训专用大模型、不搞复杂地图。牵着走一圈(teach)就能跑;新园区、新路线,几分钟内可部署。这是 GuideNav 纯视觉 VT&R 的底色,任何方案都不能牺牲它。
2. **局部 VLA 规划** — VLA 是系统的"智能层":它在局部范围内做规划与执行——理解语义目标和当前场景、处理动态障碍、泛化到示教里没见过的情形,把"固定路线的复走"升级成"理解后的导航"。GuideNav 只提供可靠骨架(定位、记忆、复走兜底)。"局部"划的是职责边界(长程记忆交给关键帧图),不是 VLA 的能力定位。
3. **越用越好用** — 系统随使用持续变好,而不是越用越退化:
   - 多轮 teach/复走叠加,LiDAR 逐步把地图建干净(见议题二 4.3);
   - teach-repeat 数据飞轮,微调出环境特定的 VLA(见议题三 5.4);
   - 地图更新机制持续修正失效路段,环境越跑越熟(见议题四)。

## 3. 适用场景与目标场景的差异(先对齐)

### 3.1 GuideNav 目前的适用场景(设计假设)

GuideNav 是为"盲人固定通勤路线"设计的,它的成立依赖几个前提:

1. **单条固定路线**:示教-重复,目的地固定(走到最后一帧);
2. **人在环内**:盲人握刚性挽具,人就是避障、应急、决策的兜底;
3. **低速**:0.15 m/s 导盲步速;
4. **白天 + 纯 RGB**:靠外观定位,不依赖 GPS/LiDAR/深度;
5. **单链拓扑**:无分支、无环、无语义;
6. **无业务产出**:不需要检测、报告、打卡。

### 3.2 园区巡检的目标场景

1. **固定路线**(这点契合),但通常是环路 + 多栋楼,单链不够;
2. **无人自主**:没有人在环内,避障和应急必须系统自己扛;
3. **更高速度**:0.5~1 m/s 才能覆盖园区;
4. **可能夜间/全天候**;
5. **有业务产出**:到点动作、异常检测、报告、打卡留痕;
6. **多路线调度、地图可更新**。

### 3.3 差异对照(核心 gap)

| 维度 | GuideNav 现状 | 园区巡检需要 | 差异性质 |
|---|---|---|---|
| 运营模式 | 人在环内 | 无人自主 | 安全模型根本不同 |
| 路线结构 | 单链固定 | 环路/多路线 | 结构需升级 |
| 速度 | 0.15 m/s | 0.5~1 m/s | 需验证提速 |
| 运营时段 | 白天 | 可能 24h | 纯视觉边界 |
| 业务产出 | 无 | 检测/报告/打卡 | 需从零新增 |
| 导航目标 | 走到终点 | 到点动作/语义目标 | 需新增 |

### 3.4 由场景差异决定的设计前提

差异本身不是问题,下面的选择才是决定后续方案走向的前提:

1. **运营时段**:白天 or 24h?—— 直接决定"纯视觉"是否成立;LiDAR 救不了夜间的视觉定位。
2. **场地**:纯室外,还是室内外混合、要进楼?—— 决定单链够不够、传感器选型。
3. **业务产出**:"到点打卡留痕"还是"发现异常报警"?—— 决定检测投入和验收标准。
4. **平台**:轮式还是四足?单台还是多台?—— 决定续航、速度、成本、调度复杂度。

## 4. 用 LiDAR 把系统做得更好、更适合业务(重点)

### 4.1 出发点

讨论的不是"要不要加 LiDAR",而是"LiDAR 在哪些环节能让巡检这件事更稳、更快、更有业务价值"。视觉与 LiDAR 分工正交:视觉管"我在哪、往哪走",LiDAR 管"前方能不能走、走多远、这条路实际长什么样"。

### 4.2 在 Repeat(运行时)的贡献:更安全、更顺

1. **安全避障** — 替代"人握挽具"。ROS2 里一个 `safety_node` 夹在 `/cmd_vel` 前,订阅 GuideNav 的 `/cmd_vel` + LiDAR 的 `/scan`/`/points`,做前方安全区检查再转发,GuideNav 代码零改动。
2. **尺度恢复** — LiDAR 深度给 Reloc3r 单位化平移补尺度,ρ 从"伪距离"变真米制,解锁提速 + 米制目标接口。
3. **动态障碍平滑** — 配合图像目标 VLA 或局部规划器,从"急停"升级到"绕障",动作更流畅。

### 4.3 在 Teach(示教时)的贡献:边教边建图,把图越建越好

这是最关键的机会:teach 不只是一遍走过录视频,而是借 LiDAR 在走的过程中,顺手把地图建得更完整。

**单次 teach 就建出"拓扑 + 度量"的图:**

1. 视觉关键帧图(现有不变);
2. LiDAR/里程计记录相邻关键帧的真实间距(尺度先验)→ 图从"纯拓扑"升级为"拓扑 + 度量";
3. LiDAR 记录沿途可通行区域、走廊宽度、静态障碍 → 轻量的"安全通道图"(free space footprint),repeat 时知道"这条路多宽、哪里常堵";
4. 给每个关键帧挂一个 6-DoF 位姿(里程计/LiDAR),后续报告定位、尺度恢复都有据可依。

**多轮 teach/复走叠加,逐步把图建干净:**

- 同一路线多走几次,LiDAR 几何信息反复叠加;
- 用"多轮观测"区分**持久结构**(墙、柱子、路缘,每次都出现)和**临时障碍**(停着的车、临时堆放,偶尔出现):持续出现 → 写进图;偶尔出现 → 只当运行时障碍;
- 这恰好解决议题四里"临时 vs 持久"最大的坑——判定依据从"一次观测"变成"多次观测",天然更稳。

**结果**:图从"一条相册"逐渐长成"带度量边、带安全通道、带持久结构标签的地图",但仍是轻量、可编辑的,没有退回重 SLAM。

### 4.4 对业务的价值(串起来看)

- 安全:无人运行有几何兜底(4.2-1);
- 效率:有尺度才敢提速(4.2-2);
- 地图质量:teach 即建图,越用越准(4.3);
- 报告定位:关键帧挂度量位姿后,报告可带米制/坐标;
- 维护成本:多轮观测自动区分持久/临时,降低人工更新负担。

### 4.5 工程取舍

1. 安全层先做"急停"还是直接"绕障"?(影响 P0 范围)
2. 地图里记多少几何:只记间距(最轻),还是记安全通道/占据(更重)?
3. teach 建图是"单次记录"还是"多轮叠加清洗"?(多轮更准,但要先跑起来)
4. 传感器:单线 2D 还是固态 3D?(室外有坡度,建议固态 3D)

## 5. VLA 模型接入(重点)

### 5.1 定位:VLA 在系统里扮演什么角色

一句话:VLA 是"通用但不完全可靠的智能",GuideNav 是"可靠但没有智能的记忆"——结合 = VLA 负责理解与决策,GuideNav 负责记忆与确定性执行。

VLA 有三个可能的插入层,别都塞在一层:

| 层 | VLA 角色 | 替代/增强什么 | 频率 |
|---|---|---|---|
| 决策层 | VLM 语义:语言目标→图节点、异常判断、调度 | "走到最后一帧"的固定目标 | 低频(目标切换/异常时) |
| 执行层 | 图像目标/PointNav VLA 输出动作 | (ρ,α,β) 控制器 | 高频(2~5Hz) |
| 记忆层 | 不替代,只消费 | CosPlace+Reloc3r 定位+记忆 | — |

### 5.2 接口怎么设计(三种 goal 形态,最关键)

VLA 吃什么 goal,直接决定好训不好训、稳不稳、部署成本:

1. **image-goal(子目标关键帧图像)** — NoMaD/OmniVLA/ViNT 谱系,把"往前走一帧的画面"喂给 VLA。优点:零接口改造、天然绕障、与 GuideNav 子目标选择天然一致;缺点:相似走廊图像目标会歧义。
2. **PointNav(米制相对坐标)** — Qwen-RobotNav 谱系,给 (x,y,θ)。优点:可解释、可控、直接接 LiDAR 尺度;缺点:要尺度恢复 + 坐标变换,接口桥有活。
3. **language(语言指令)** — ABot-N1/慢系统谱系,"去3号楼"。优点:最贴合业务;缺点:慢、重,只适合决策层,不适合高频控制。

**建议**:决策层用 language/VLM,执行层用 image-goal 或 PointNav,不要用语言直接驱动高频动作。

### 5.3 慢-快双系统(推荐架构)

```
语言目标("去3号楼")
  → 慢系统 VLM(低频):检索关键帧图 → 目标/中间节点
  → GuideNav 定位层:CosPlace + Markov → 当前节点
  → 快系统 VLA(高频):image-goal/PointNav 执行"当前→子目标"
  → 低层安全层(LiDAR)
```

与 ABot-N0/N1 的慢-快架构一致;GuideNav 的关键帧图 + 定位层正好对应其 Topo-Memory + Visual Localization。

### 5.4 数据飞轮:teach-repeat 是免费的微调数据(VLA 主场)

这是纯云端方案做不到的:每次 teach/repeat 都在**部署环境本地**产生对齐的 (观测, 相对位姿, 动作) 三元组,可减少仿真到真实的分布差异，但仍需同步、质检和失败样本筛选。

- 冷启动:teach 数据 SFT/LoRA 出一个环境特定小 VLA;
- 持续:repeat 中 DAgger 式采集,专家(GuideNav 控制器/人工)标注,迭代变好;
- 结果:VLA 在这个园区越跑越准。

### 5.5 部署与算力

- 执行层快系统:优先小模型——NoMaD 19M 扩散策略(开源),Orin 可跑;ABot-N1 边缘 306M DiT;
- 决策层慢系统:VLM 2-8B 按需调用,不必每帧;
- VLA 与 Reloc3r 不必同频:VLA 2~5Hz 异步,航点跟踪器 10Hz 复用缓存(见 [GuideNav 与 VLA 融合：记忆、目标接口与局部执行](/blog/2026/2026-09-29-guidenav-vla-integration) 附录 A.5)。

### 5.6 失效与回退(VLA 不可靠是前提,不是意外)

不同任务的 VLA 成功率不可直接横比；系统必须设计失效回退：
- 回退阶梯:安全层 > VLA > (ρ,α,β) 控制器 > 停车;
- VLA 失败(超时/低置信)回退 GuideNav 原版控制器,仅在定位可信、路径可通行时低速复走，否则停车。

### 5.7 工程取舍

1. 执行层用 image-goal 还是 PointNav?(决定接口桥工作量)
2. 慢-快是"全边缘"还是"慢系统上云"?(全本地 vs 网络依赖)
3. VLA 微调环境特定小模型,还是通用大模型 zero-shot?(数据飞轮 vs 冷启动)
4. 异常判断交给 VLM 还是专用检测模型?(开放 vs 已知)

## 6. 地图更新(重点)

### 6.1 为什么重要

地图是 VT&R 的核心资产,不是 teach 一次就一劳永逸。园区会持续变化:季节、装修施工、长期停放的车辆、新建楼、改路线。地图更新的能力,决定系统是"能用两周"还是"能长期运营"。

### 6.2 三个子问题

1. **什么变化需要更新?(触发条件)**
   - 短期动态(行人/车经过)→ 不更新,交给安全层
   - 中期变化(季节/装修/长期停放)→ 局部重示教
   - 长期变化(新建楼/改道)→ 整段重新 teach
2. **更新到多大粒度?**
   - 单链天生可编辑:删一张图 = 删一段路,拼目录重编号 = 拼路线
   - 拆段后更新爆炸半径小:只重 teach 变化的那一段,其余段不动
3. **谁来更新?**
   - 人工:牵着重新走一圈(几分钟,最可靠)
   - 自动:机器人检测到失效,自动采新帧
   - 半自动:机器人标失效段,人确认后重 teach(推荐)

### 6.3 关键技术点

1. **失效检测信号**:Markov 信念发散 / Reloc3r 共视失败率 / CosPlace top-1 相似度持续下降 → 汇总成"地图健康度"指标。
2. **局部重示教 + 拼接**:找失效段的起止关键帧 → 替换中间 → 重新编号。单链结构下比 SLAM 重建 + 回环对齐简单一个量级。
3. **描述符库增量重建**:只重算新增/替换帧的 `.h5`,不必全量重建。
4. **版本管理**:每次更新 = 新版本,保留旧版可回滚(比如施工期用旧版)。

### 6.4 最大的坑

自动更新会把"临时变化"误写成"持久变化"——一辆停了三天终于开走的车,如果被写进地图,反而把路记错。区分持久 vs 临时变化(变更检测)本身很难。所以推荐:**自动检测 + 人工确认,不要做全自动写图**。

### 6.5 工程取舍

1. 更新频率:定时(每周人工重 teach)还是事件触发(定位置信度下降才更新)?
2. 全自动 vs 半自动:是否接受"人在回路确认"?
3. 要不要地图版本管理 + 回滚?

## 7. 其他技术决策

1. **路线结构**:单链拆段 vs 升级图结构(edges.json)。建议先拆段,图结构推迟。
2. **速度**:目标 0.5~1m/s,要验证 4Hz 控制 + Reloc3r 帧间共视在大速度下是否稳定。
3. **检查点与报告**:拓扑位置(检查点名)够不够?要不要挂 RTK/GPS 坐标?—— 多数巡检"检查点 + 时间戳 + 照片"就够,别急着上 SLAM。

## 8. 落地阶段

- **P0**:单条固定路线 + LiDAR 安全急停,在受控场地验证路线完成率、干预次数与停车响应
- **P1**:检查点打标 + 到点拍照/上传 + 报告
- **P2**:异常检测模型接入 + VLA 执行层(图像目标,替换控制器)
- **P3**:多路线调度、环线处理、丢失重定位、地图更新机制、夜间方案、VLM 语义目标(慢系统)

## 9. 验证顺序与评估指标

先在一条受控路线验证定位和安全停车，再增加检查点动作、异常检测与多路线调度。每次扩展都应保留同一套回归路线，以判断新增模块是否影响原有能力。

| 验证对象 | 需要记录的证据 |
| --- | --- |
| 定位与复走 | 完成率、错误重定位次数、人工干预次数、不同光照下的退化 |
| 局部绕障 | 最小间距、碰撞或接触次数、绕行后恢复路线的比例 |
| 检查点动作 | 到点误差、照片或检测结果完整率、重复触发与漏触发 |
| 地图更新 | 变化识别准确性、错误写入比例、旧版本回滚是否可用 |
| 持续运行 | 温度、时延分位数、续航和网络中断下的行为 |

## 10. 结语

GuideNav 的价值在于把重复路线压缩成可检索、可维护的视觉记忆。巡检系统还需要任务编排、局部几何和独立安全控制。将这些职责拆清楚，再逐项验证，比把全部能力寄托在一个导航模型上更容易定位问题与维护系统。
