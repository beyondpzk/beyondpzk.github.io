# 户外长距离导航：全局路由、局部策略与数据闭环

> 基于公开论文整理的工程设计思路。路线、店铺、坐标、数据量与阶段安排均为示意，不对应实际行程或项目记录；系统流程中的扩展设计不代表各论文已验证的能力。

## 导航模型与任务编排

ABot-N0、ABot-N1、Qwen-RobotNav 都面向复杂导航，但它们对"复杂"的解法截然不同。在确定本方案的架构之前，先把三者的差异讲清楚。

### 核心差异：谁来做"拆解"？

复杂导航的本质矛盾是：**单一模型的感知范围和推理深度都不足以覆盖数公里的开放环境**。因此三个系统都必须引入某种"拆解"机制——把长程任务切成短程子任务。差异在于**谁来拆、用什么信息拆、拆完之后怎么接起来**。

| 维度 | ABot-N0 | ABot-N1 | Qwen-RobotNav |
|---|---|---|---|
| **谁来拆解** | 独立的外部 Agentic Planner（VLM） | 无内置 Planner；依赖外部系统拆好后喂入 | 独立的外部 Planner（LLM，Qwen3.6-Plus） |
| **拆解依据** | 用户意图 → CoT → 子任务序列 + Topo-Memory 位置信息 | 不拆解；接收已拆好的单段子任务 | 用户意图 + 高德/地图路由 → 子任务序列 + 观察配置 |
| **记忆机制** | 四层 Topo-Memory（Block/Road/Function/Object-POI），持续读写 | 仅图像帧构成的 visual memory，无长期世界模型 | Evidence Notebook：关键帧索引 + 文本摘要 |
| **失败恢复** | Self-Reflector 判断子任务是否完成 → 未完成则写回 Topo-Memory → Planner 重规划 | 无内置失败恢复；失败后需外部系统重新分配子任务 | Planner 根据 Evidence Notebook 决定重试/换策略/换模式 |
| **模型角色** | 执行器：接收子任务，输出 5 个 BEV 航点 | 全栈执行器：接收子任务，slow VLM 输出 pixel goal → fast VLA 输出航点 | 被调用工具：接收 (指令, 模式, 观察配置)，输出 8 个局部航点 |

### ABot-N0：最完整的 Agentic 系统

```
用户: "带我去示例咖啡店"
        ↓
Agentic Planner (云端 VLM)
  ├── 意图解析: 目标 = 最近示例咖啡店
  ├── Topo-Memory 检索: 已知示例咖啡店在商场B1
  ├── 子任务拆解:
  │   g₁ = Point-Goal → 走出小区
  │   g₂ = Point-Goal → 沿人行道走到商场路口
  │   g₃ = POI-Goal → 找到商场入口
  │   g₄ = Object-Goal → 到达B1示例咖啡店
  └── 每个 gᵢ 交由 ABot-N0 执行
        ↓
Self-Reflector 每段完成后评估
  ├── 成功 → 更新 Topo-Memory (示例咖啡店/可达)
  └── 失败 → Topo-Memory 标记不可达 → Planner 重规划
```

ABot-N0 的完整 Agentic 系统包括四个模块：Agentic Planner、Actor (ABot-N0 模型)、Episodic Memory、Topo-Memory。它的核心优势是**闭环**：任务执行结果会写回记忆，影响后续决策。缺点是需要云端 Planner 持续在线，且系统复杂度最高。

### ABot-N1：把复杂性压缩进双系统

```
外部系统先把任务拆好，逐段喂入:

子任务: "沿人行道走到前方路口，看到麦当劳右转"
        ↓
Slow VLM (~1Hz, 4B)
  ├── CoT 推理: "前方人行道畅通，右侧约50m处有麦当劳招牌"
  ├── Affordance Pixel: 前方3m处人行道中央
  └── Target Pixel: 麦当劳招牌在画面中的位置
        ↓
Fast VLA (~10Hz, 2B/306M)
  └── 持续跟踪两个pixel → 生成5个SE(2)航点
```

ABot-N1 没有独立的 Planner/Topo-Memory/Self-Reflector。它的 Slow VLM 只做 deliberative reasoning（看图后决定下一步往哪走），不做子任务拆解。复杂导航的长程拆解必须由**外部系统**（可以是另一个 LLM/VLM）完成。优点是架构简洁、五任务统一为 pixel-goal 接口；缺点是无法独立完成长程导航。

### Qwen-RobotNav：模型是工具，Planner 是大脑

```
Planner (Qwen3.6-Plus, 云端)
  ├── 接收用户指令
  ├── 调用高德 API 获取路由
  ├── 拆解为分段子任务，每段指定:
  │   τ_i = {mode, instruction, goal_coord, obs_config}
  ├── 逐段调用 Qwen-RobotNav:
  │   POST /nav {mode: "VLN", instruction: "...", γ:2.0, B:3072}
  └── 每段执行后:
      ├── 接收 Evidence (关键帧 + 文本摘要)
      ├── 判断是否完成
      └── 更新 Evidence Notebook
        ↓
Qwen-RobotNav (边缘, 4B/8B)
  └── 接收 (L_i, τ_i, Φ_i) → 输出 8 个局部航点
```

Qwen-RobotNav 的设计哲学是"薄执行器 + 厚规划器"。模型本身只是一个导航原语，真正复杂的是 Planner。这种设计的最大优点是 **Planner 可以独立升级**（换更强的 LLM，不需要重训导航模型），而且观察配置参数化让同一个模型可以适配不同任务模式。缺点和 ABot-N0 一样，需要云端 Planner。

### 本方案的取舍

结合三者的优缺点，本方案采用：

- **Planner 层**：采用 ABot-N0 的 Agentic Planner + Topo-Memory + Self-Reflector 闭环，但 Planner 的调用接口采用 Qwen-RobotNav 的参数化模式（给每段子任务同时指定 mode、指令、坐标和观察配置）。
- **执行层**：采用 ABot-N1 的 Slow-Fast 双系统，用 pixel goal 作为跨任务的统一接口，同时保留 Qwen-RobotNav 的多模式能力（VLN/PointNav/ObjNav/Safety）。
- **L0 安全层**：独立于以上所有模型，硬实时规则兜底。

这样，系统同时具备：完整的任务拆解与长期记忆（ABot-N0）、简洁统一的执行架构（ABot-N1）、灵活的模式切换与观察配置（Qwen-RobotNav）。

## 同一任务的三条执行路径

下面以同一个任务为例——**"从当前位置出发，到 10 公里外的示例咖啡店门口"**——完整走一遍三个系统各自的执行过程。

### 前置：高德 API 返回什么

三个系统都依赖高德，高德返回的原始信息是相同的：

```
高德 POI 搜索: "示例咖啡店" → 最近门店 lat=<目标纬度>, lng=<目标经度>
高德步行路径:
  [起点] → 300m 沿示例道路 A西行 → 路口A右转 →
  500m 沿示例道路 B北行 → 路口B过斑马线 →
  ...(中间省略 15 个 waypoint)...
  → 100m 沿商场外围步行 → [示例咖啡店入口]
全程 10.2km, 预计 2h15min
```

关键事实：高德 waypoint 是**路口/路段中心点**，精度约 1~5 米，且**不区分人行道和车行道**。三个系统都必须解决"粗坐标 → 可执行局部目标"的问题，但解法不同。

### ABot-N0 的执行过程

```
Step 1: 用户说话
  "带我去 10 公里外那个示例咖啡店"
        ↓
Step 2: Agentic Planner (云端 VLM) 启动
  ├── 高德 POI 搜索 → 找到最近示例咖啡店
  ├── 高德路径规划 → 拿到 18 个 coarse waypoint
  ├── Topo-Memory 检索: 这条路走过 3 次，路口中途有个施工点已知不可达
  ├── VLM 推理: "高德让我在路口A右转，但我记得那个路口右侧在施工，
  │              需要提前从上一个斑马线过马路，走对面人行道"
  ├── 生成修正后的子任务序列:
  │   τ₁ = {mode: "PointNav", goal: "dx=47, dy=12", note: "走出小区"}
  │   τ₂ = {mode: "VLN", instruction: "前方路口过斑马线，走对面人行道",
  │          note: "避开施工"}
  │   τ₃ = {mode: "PointNav", goal: "dx=83, dy=5", note: "沿对面人行道走"}
  │   ...（共约 20~30 段，每段 50~200m）
  │   τ_N = {mode: "POI-Goal", target: "示例咖啡店", note: "找到商场入口"}
  └── 每段 τ_i 串行发送给边缘 ABot-N0
        ↓
Step 3: 边缘 ABot-N0 逐段执行
  对于 τ₂（VLN 段）:
    当前 RGB 观测 → ABot-N0 Brain (Qwen3-4B) →
      理解指令 "过斑马线走对面" →
      生成 5 个 BEV 航点: [(+1.2, 0, 0°), (+2.5, 0, 0°), ...]
      → Neural Controller → 机体速度
  对于 τ_N（POI-Goal 段）:
    当前 RGB 观测 → Brain 识别 "示例咖啡店" 招牌 →
      判断入口位置 → 生成精细航点序列 →
      精确到达入口 2m 范围内
        ↓
Step 4: 每段执行后 Self-Reflector 评估
  τ₂ 执行完:
    Self-Reflector: "机器人当前位置是否在马路对面人行道上？"
    → 是 → 标记 τ₂ 完成 → 更新 Topo-Memory（施工点/已绕行）
    → 进入 τ₃
  τ₅ 执行时（假设前方临时封路）:
    ABot-N0 连续 3 步无法前进 →
    Self-Reflector: "τ₅ 失败，原因 = 前方临时路障" →
    写回 Topo-Memory（该路段/不可达）→
    Planner 请求高德重新规划绕行路线 →
    生成新的 τ₅' → 继续执行
        ↓
Step 5: 到达
  τ_N 完成 → Self-Reflector 确认 "当前位置距示例咖啡店入口 < 2m" →
  任务完成 → Topo-Memory 写入（示例咖啡店/确认可达）
```

ABot-N0 的关键特征：
- **Planner 是有记忆的**（Topo-Memory 记住了施工点和历史成功路径）。
- **失败可以闭环恢复**（Self-Reflector → Topo-Memory → Planner 重规划）。
- **但云端 Planner 必须全程在线**，每段执行结果要上报。

### ABot-N1 的执行过程

ABot-N1 本身没有 Planner/Topo-Memory/Self-Reflector。要完成这个任务，**必须有一个外部系统**（假设叫 External Orchestrator）来拆解和调度。

```
Step 1: 用户说话
  "带我去 10 公里外那个示例咖啡店"
        ↓
Step 2: External Orchestrator 拆解
  ├── 高德 POI 搜索 → 找到最近示例咖啡店
  ├── 高德路径规划 → 拿到 18 个 coarse waypoint
  ├── Orchestrator 自己的逻辑（可以是 LLM/VLM，但不是 ABot-N1 的一部分）:
  │   "把高德路径拆成 20 段，每段 200~500m"
  ├── 对每段做坐标精修或语义转换:
  │   段1: 粗坐标 (lat1,lon1) → 回传当前画面 → VLM 精修为 (dx=47,dy=12)
  │   段2: 粗坐标 (lat2,lon2) → 回传画面 → VLM 判断该路口 → VLN 指令
  │   ...
  └── 生成子任务列表，逐段下发
        ↓
Step 3: ABot-N1 逐段执行
  对于每段子任务 τ_i:
    Slow VLM (~1Hz):
      输入: 三视角 RGB + 历史帧 + τ_i 的目标（坐标或指令）
      输出: CoT + Affordance Pixel + (可选) Target Pixel
      例如 τ₂（VLN 段）:
        CoT: "前方50m为路口，斑马线可见，红灯，需要等待"
        Affordance Pixel: 斑马线起点位置
        Target Pixel: 马路对面人行道入口
    Fast VLA (~10Hz):
      跟踪像素目标 → 输出 5 个 SE(2) 航点 → 机器人行走
        ↓
Step 4: 段间切换
  Orchestrator 检测到 ABot-N1 输出的航点序列中出现 "到达标志" →
  判断当前段完成 → 下发下一段 τ_{i+1}
        ↓
Step 5: 失败处理
  τ₅ 执行时遇到临时路障:
    ABot-N1 没有 Self-Reflector，只能继续尝试或由 Fast VLA 局部绕行
    如果局部绕行失败 → 机器人停止 →
    Orchestrator 通过 GPS/图像判断位置异常 →
    Orchestrator 决定: "这一段需要重试" 或 "请求高德重新规划"
    → 生成新的 τ₅' → 重新下发
        ↓
Step 6: 到达
  Orchestrator 通过 GPS 判断 "距示例咖啡店 < 2m" → 任务完成
```

ABot-N1 的关键特征：
- **模型本身只管"这一段怎么走"，不管"10 公里怎么拆"**。
- **没有长期记忆**：走过一次的路，下次不会自动记住。
- **失败恢复依赖 Orchestrator**：ABot-N1 自身不判断子任务是否完成，也不会触发重规划。
- 好处是架构简单，如果 Orchestrator 做得好，ABot-N1 的 Slow-Fast 在单段内执行质量很高。

### Qwen-RobotNav 的执行过程

Qwen-RobotNav 的模型本身跟 ABot-N1 类似——只做局部执行。但它的 Planner 设计更标准化。

```
Step 1: 用户说话
  "带我去 10 公里外那个示例咖啡店"
        ↓
Step 2: Planner (Qwen3.6-Plus) 启动
  ├── 高德 POI 搜索 → 找到最近示例咖啡店
  ├── 高德路径规划 → 拿到 18 个 coarse waypoint
  ├── Planner 推理: "18 个 waypoint，每 2~3 个合并为一段，
  │              每段 200~500m，共 8 段"
  ├── 为每段选择模式和观察配置:
  │   τ₁ = {mode: "PointNav", goal: (47,12), γ:1.5, B:2560,
  │          instruction: "沿人行道直行"}
  │   τ₂ = {mode: "VLN", γ:2.0, B:3072,
  │          instruction: "前方路口右转，过斑马线后沿示例道路 B走"}
  │   τ₃ = {mode: "Safety", γ:3.0, B:2048,
  │          instruction: "在路口等待红绿灯"}
  │   ...（共约 8~12 段）
  │   τ_end = {mode: "ObjNav", γ:2.5, B:4096,
  │            instruction: "找到示例咖啡店的门口"}
  └── 串行调用 Qwen-RobotNav
        ↓
Step 3: Qwen-RobotNav 被调用
  对于 τ₂（VLN 段）:
    Planner 发送:
      POST /execute_nav {
        mode: "VLN",
        instruction: "前方路口右转，过斑马线后沿示例道路 B走",
        obs_config: {γ: 2.0, B: 3072, m: "latest"}
      }
    Qwen-RobotNav 边缘推理:
      参数化观察编码根据 γ=2.0 偏重近期帧 →
      视觉编码器处理 RGB → LLM 骨干理解指令 →
      4 层 MLP 输出 8 个局部航点
    Robot 执行航点
    Harness 收集: 关键帧 × 3 + 文本摘要 "已到达路口，斑马线可见"
        ↓
Step 4: 每段执行后 Planner 评估
  Planner 收到 Evidence:
    "τ₂ 完成，当前位置在示例道路 B人行道，前方无异常"
  → 更新 Evidence Notebook:
    {segment: 2, status: "done", position: (30.28, 120.13), note: "路口无施工"}
  → 下发 τ₃
        ↓
Step 5: 失败处理
  τ₅ 执行时 Evidence 显示 "机器人位置异常，偏离预定路径 15m":
    Planner 判断:
    ├── Evidence Notebook 显示 τ₄ 正常完成
    ├── GPS 显示当前位置在车行道上
    ├── 决策: "这可能是 GPS 漂移" → 请求边缘回传当前画面
    ├── 看到画面: 确实在马路中间（实际偏离）
    └── 决策: "τ₅ 失败，原因 = 偏离人行道" →
        重试 τ₅，切换到 PointNav 模式，用精修坐标导航回到人行道
        ↓
Step 6: 到达
  τ_end 完成 → Evidence 显示 "距示例咖啡店入口 < 2m" →
  Planner 标记任务完成 → 写入 Evidence Notebook（示例咖啡店/可达/路径有效）
```

Qwen-RobotNav 的关键特征：
- **Planner 和模型是松耦合的**：Planner 可以随时升级 LLM 版本，不影响模型。
- **观察配置参数化**：每个子任务根据需求调整 `(γ, B, m)`，长途用大 B 保留全局上下文，路口用大 γ 偏重眼前。
- **Evidence Notebook 是轻量记忆**：不构建空间拓扑，只记关键帧和文本摘要，比 Topo-Memory 轻量但信息量也更少。
- **模型是无状态的**：不会记住上一段的内容，完全靠 Planner 传上下文。

### 三条路径的关键差异总结

| | ABot-N0 | ABot-N1 | Qwen-RobotNav |
|---|---|---|---|
| **谁做 10km 拆解** | 内置 Agentic Planner (VLM) | 外部 Orchestrator | 内置 Planner (LLM) |
| **拆解粒度** | 细（20~30 段，50~200m/段） | 取决于 Orchestrator | 中（8~12 段，200~500m/段） |
| **粗坐标精修** | Planner VLM 看图精修 | Orchestrator 看图精修 | Planner 可在收到 Evidence 后再精修 |
| **记忆** | Topo-Memory 四层，持续读写 | 无 | Evidence Notebook（关键帧 + 文本） |
| **失败恢复** | Self-Reflector → Topo-Memory → 重规划（闭环） | Orchestrator 检测 → 重下发（开环） | Planner 根据 Evidence 决策（半闭环） |
| **模型是否有状态** | 有（Episodic Memory） | 有（visual memory，仅限当前段） | 无（完全无状态） |
| **Planner 可独立升级** | 否（Planner 是系统的一部分） | 是（Orchestrator 独立） | 是（Planner 独立于模型） |
| **离线能力** | 差（Planner 在云端） | 中（Orchestrator 可部署在边缘） | 差（Planner 通常云端） |
| **系统复杂度** | 高 | 低（模型侧简单） | 中 |

三条路径的共同点：**单一模型无法覆盖 10 公里**。差别在于拆解这件事是交给内置的 Agentic 系统（ABot-N0）、外部 Orchestrator（ABot-N1）、还是标准化 Planner 接口（Qwen-RobotNav）。


## ABot-N0 与 ABot-N1 的粗坐标精修逻辑对比

粗坐标精修是高德集成中最关键的步骤之一。高德返回的路口中心点（精度 1~5 米）不能直接作为 PointNav 目标，必须精修为"人行道上的可执行坐标"或"语义导航指令"。ABot-N0 和 ABot-N1 在这一步的逻辑**本质相同，但执行位置和执行者不同**。

#### 精修逻辑本身：三段式流水线

无论是哪个系统，粗坐标精修的算法核心都是一样的三段式流程：

```
高德粗坐标 (lat, lng) ——精度 1~5m，路口/路段中心点
        │
        ▼
  [Step 1] 获取当前画面
  机器人拍摄当前位置的前向 RGB 图像
        │
        ▼
  [Step 2] VLM 看图定位
  "在这个画面里，目标路口/目标 POI 在哪里？"
  VLM 输出：目标在图像中的像素坐标 (u, v) 和深度估计
        │
        ▼
  [Step 3] 像素 → 局部坐标投影
  通过单目深度估计，将 (u, v) 投影到地面平面
  → 得到局部相对坐标 (dx, dy) ——以机器人为原点的可执行目标
```

如果 Step 2 失败——目标被遮挡、距离太远、不在当前画面中——则走语义转换分支：

```
VLM 无法定位目标
        │
        ▼
  [Fallback] 语义转换
  "前方路口右转，沿示例道路 B走 500 米，看到示例咖啡店招牌停下"
  将粗坐标替换为 VLN 自然语言指令
```

#### 差异一：谁来做

| | ABot-N0 | ABot-N1 |
|---|---|---|
| **执行者** | Agentic Planner（云端 VLM） | 外部 Orchestrator（不在 ABot-N1 内） |
| **时机** | 子任务下发前，Planner 主动精修每一段 | Orchestrator 在逐段下发前精修 |
| **视觉输入** | Planner 通过 4G/5G 获取边缘回传的当前画面 | Orchestrator 获取边缘回传的画面 |

核心区别：精修逻辑不是 ABot-N1 的一部分。ABot-N1 的 Slow VLM 不做粗坐标精修——它在收到子任务时，目标已经是精修过的（相对坐标或语义指令）。Slow VLM 做的是**更局部**的事情：在当前画面中找一个可通行的 pixel goal，而不是"AMap 的粗坐标对应画面里哪个位置"。

#### 差异二：精修时的上下文

| | ABot-N0 | ABot-N1 |
|---|---|---|
| **可利用的记忆** | Topo-Memory（历史 POI 位置、已知路标、成功/失败路径） | Orchestrator 自行维护的上下文（如果有的话） |
| **多模态输入** | 当前画面 + 高德 waypoint + 任务目标 + Topo-Memory 检索结果 | 当前画面 + 高德 waypoint + 任务目标 |
| **精修质量的影响因素** | Topo-Memory 可以提供额外锚点（如"上次示例咖啡店在商场 B1 入口左侧"） | 完全依赖当前画面和高德坐标 |

在 ABot-N0 里，Planner 精修坐标时可以利用 Topo-Memory 中的历史信息。例如：

- Topo-Memory 记录过"示例咖啡店入口在商场东南角，面对公交站"；
- Planner 在精修 τ_N 时，即使示例咖啡店招牌被树遮挡，仍能根据商场东南角和公交站的位置推断入口坐标。

ABot-N1 的外部 Orchestrator 要做同样的事，需要自己维护等价的上下文。

#### 差异三：精修后的目标交给谁

精修完成后，两种系统对精修结果的使用方式也不同：

**ABot-N0：精修结果 → ABot-N0 基础模型**

```
Planner 精修: (lat, lng) → (dx=47, dy=12)
        ↓
ABot-N0 接收: {goal: (47, 12), mode: "PointNav"}
        ↓
ABot-N0 Brain (Qwen3-4B) 直接推理 →
  "目标在右前方 47m，沿当前人行道直行" →
  Action Expert → 5 个 BEV 航点
```

ABot-N0 拿到的是**已经精修好的局部坐标**，不需要再对 AMap 粗坐标做任何处理。

**ABot-N1：精修结果 → Slow VLM 做像素级二次精修**

```
Orchestrator 精修: (lat, lng) → (dx=47, dy=12) 或 VLN 指令
        ↓
ABot-N1 Slow VLM 接收: {goal: (47, 12), instruction: "沿人行道直行"}
        ↓
Slow VLM 推理 →
  在当前画面中定位: "前方人行道畅通，目标在右前方约 47m 处" →
  输出 Affordance Pixel: 画面中前方 3m 人行道中心点 →
  输出 Target Pixel: 画面中 47m 处人行道可见位置（如果可见）
        ↓
Fast VLA 跟踪两个 pixel → 5 个 SE(2) 航点
```

ABot-N1 的 Slow VLM 虽然不负责"AMap 粗坐标精修"，但它做的**像素级定位**本质上是第二层精修：把 "47m 前方" 这种相对坐标再转化为画面中具体的像素位置。这是一种**两层精修结构**：

1. 第一层（外部）：AMap 粗坐标 → 局部相对坐标（Orchestrator/Planner）
2. 第二层（ABot-N1 内部）：局部相对坐标 → 画面 pixel goal（Slow VLM）

而 ABot-N0 只有第一层，ABot-N0 的 Brain 不输出 pixel goal，直接输出 BEV 航点。

#### 差异四：语义转换的分工

当粗坐标无法精修（目标不在画面中），两个系统的处理方式：

| | ABot-N0 | ABot-N1 |
|---|---|---|
| **谁做语义转换** | Agentic Planner | 外部 Orchestrator |
| **转换产物** | VLN 指令文本 | VLN 指令文本 |
| **执行方式** | ABot-N0 以 VLN 模式接收指令 | ABot-N1 Slow VLM 理解指令 → CoT + pixel goal |

在这一步，两个系统的逻辑基本一致：都是 VLM 把坐标转为自然语言指令，再交给模型以 VLN 模式执行。差别仍然只是"谁来做"——ABot-N0 的 Planner 内部完成，ABot-N1 依赖外部 Orchestrator。

#### 总结

| 维度 | ABot-N0 | ABot-N1 |
|---|---|---|
| 精修算法核心 | 三段式（画面→VLM 定位→投影），两者相同 | 同左 |
| 精修执行者 | 内置 Agentic Planner | 外部 Orchestrator（不在 ABot-N1 内） |
| 精修时可用的记忆 | Topo-Memory（历史 POI、路径） | Orchestrator 自行维护 |
| 精修产物 | 局部坐标或 VLN 指令 | 同左 |
| 模型侧是否做二次精修 | 否（直接输出 BEV 航点） | 是（Slow VLM 做 pixel goal 定位） |
| 语义转换执行者 | Planner 内部 | Orchestrator 内部 |

一句话总结：**精修的逻辑是相同的三段式，但 ABot-N0 把它内建在 Agentic Planner 里（有 Topo-Memory 加持），ABot-N1 把它完全外包给外部系统。此外 ABot-N1 的 Slow VLM 还多做一层像素级二次精修。**


## VLM 精修能力的训练方法与 GT 数据制作

前文梳理了精修逻辑的执行流程。这一节回答更深层的问题：**ABot-N0 的 Planner VLM 和 ABot-N1 的 Slow VLM，是怎么学会"看图定位目标"这个能力的？GT 数据是怎么做出来的？**


### ABot-N0 的 Planner VLM 训练

ABot-N0 的 Planner 不是拿一个现成 VLM 直接做 zero-shot 推理。它被训练为一个 **通用奖励模型（General Reward Model）**，训练数据约 **5.0M 推理样本**，共 6 类辅助任务，其中三类直接支撑精修能力、三类间接支撑：

**（一）POI Grounding — 0.5M 条**

这是精修能力最直接的训练数据。

| 维度 | 说明 |
|---|---|
| 数据形式 | `<POI 名称, 入口像素坐标 (u, v)>` 的 VQA 对 |
| 数据来源 | 从 BridgeNav 数据集筛选街景图像 |
| GT 制作 | 使用 Qwen3-VL-Plus 自动生成结构化标注，再人工校验 |
| 训练目标 | 给定街景图像和 POI 名称（如"示例咖啡店"），VLM 输出该 POI 入口在图像中的像素坐标 |
| 对精修的作用 | Planner 在精修 POI-Goal 段时，就是执行这个任务——"画面里的示例咖啡店入口在哪？" |

GT 制作流程：

```
BridgeNav 街景图像（含 POI 名称和物理入口位置）
        ↓
Qwen3-VL-Plus 自动标注
  输入: 图像 + "请标出示例咖啡店的入口位置"
  输出: 入口像素坐标 (u, v)
        ↓
人工校验: 剔除明显错误的标注（如入口被遮挡、标注到隔壁店铺）
        ↓
最终 GT: 0.5M 条 VQA 对
```

**（二）Navigable Areas Analysis — 1.2M 条**

| 维度 | 说明 |
|---|---|
| 数据形式 | 户外 egocentric 图像 + 可通行区域多边形（人行道、斑马线） |
| 数据来源 | 户外视频流采集 |
| GT 制作 | **人工标注**：标注员在图像上画出可通行区域的多边形边界，明确排除车行道、草坪、花坛 |
| 训练目标 | VLM 根据图像输出可通行区域的语义标签和多边形坐标 |
| 对精修的作用 | Planner 在精修坐标时，必须知道"画面上哪些地方能走"——目标坐标不能落在车行道上。这个数据集训练 VLM 判断可通行区域。 |

**（三）Instruction-Following Reasoning — 1.3M 条**

| 维度 | 说明 |
|---|---|
| 数据形式 | 长指令 → 子指令 + 里程碑节点（时空终止点） |
| 数据来源 | VLN-CE R2R/RxR 的 30,000 个 clips |
| GT 制作 | Gemini-3 Pro + Qwen3-VL 自动处理，生成子指令和对应的里程碑节点 |
| 训练目标 | VLM 把长指令分解为可执行的子指令序列，并为每段标注终点 |
| 对精修的作用 | Planner 在拆解高德长路径时，就是执行类似的任务——"这条 500m 的路径，在哪个路口该转弯？转弯后目标点在哪？" |

对精修的作用 | Planner 在拆解高德长路径时，就是执行类似的任务——"这条 500m 的路径，在哪个路口该转弯？转弯后目标点在哪？"

**（四）Social Navigation CoT — 0.8M 条（间接支撑）**

| 维度 | 说明 |
|---|---|
| 数据形式 | 户外场景图像 + 结构化 CoT 推理链 |
| 数据来源 | SocialNav 流水线自动生成 |
| GT 制作 | 以 Qwen-VL-Max 作为教师，生成决策背后的显式逻辑，如"交通灯是红色，因此必须等待""有行人从左侧接近，减速靠右" |
| 训练目标 | VLM 学会在导航中输出社会规则推理 |
| 对精修的作用 | Planner 精修坐标时，若目标点位于需要社会判断的位置（如斑马线前、人行道与车行道交界），CoT 推理能力帮助它做出正确的安全判断 |

**（五）Object-Goal Reasoning — 0.1M 条（间接支撑）**

| 维度 | 说明 |
|---|---|
| 数据形式 | 四步推理链：目标可见性 → 空间关系 → 路径规划 → 原子动作 |
| 数据来源 | 基于 OVON 数据集生成 |
| GT 制作 | 自动生成 + 一致性过滤：仅保留与真值轨迹对齐的样本 |
| 训练目标 | VLM 学会推理目标物体的空间位置和到达策略 |
| 对精修的作用 | 当 Planner 需要精修 Object-Goal 类子任务（如"找到示例咖啡店的门口"）时，这个能力帮助它判断目标是否可见、怎么走过去 |

**（六）General VQA — 1.1M 条（基础能力）**

| 维度 | 说明 |
|---|---|
| 数据形式 | 通用视觉问答、图像描述、视觉定位 |
| 数据来源 | Blip3、COCO、MAmmoTH-VL、RefCOCO、Objects365、R2R-EnvDrop、ScanQA 等 |
| GT 制作 | 各数据集自带标注 |
| 训练目标 | 保持 VLM 的通用视觉-语言表征能力，防止在专项导航数据上过拟合 |
| 对精修的作用 | 不直接参与精修，但为前述五类专项能力提供了稳定的基础视觉理解 |

**六类数据汇总：**

| 类别 | 规模 | 与精修的关系 |
|---|---|---|
| POI Grounding | 0.5M | **直接**——训练 VLM 在画面中定位 POI 入口 |
| Navigable Areas Analysis | 1.2M | **直接**——训练 VLM 判断可通行区域 |
| Instruction-Following Reasoning | 1.3M | **直接**——训练 VLM 拆分长指令 |
| Social Navigation CoT | 0.8M | 间接——社会规则推理 |
| Object-Goal Reasoning | 0.1M | 间接——目标物体空间推理 |
| General VQA | 1.1M | 基础——通用视觉-语言能力 |
| **合计** | **5.0M** | |

**（七）Planner 的训练范式：Policy + Critic 双模式**

```
训练数据: 成对观测 + 语言目标
        ↓
General Reward Model 训练
  ├── Policy 模式: "当前状态 → 下一步做什么（拆解/调整方向）"
  └── Critic 模式: "当前状态离目标有多远 → 是否完成"
        ↓
同一个 VLM 同时拥有:
  - 任务拆解能力（Policy）
  - 完成评估能力（Critic / Self-Reflector）
```

Planner 的"精修"能力不是独立训练的，而是 Policy 模式的一个子能力：当 Policy 模式被问及"高德说目标在 (lat, lng)，但从画面看具体在哪？"时，VLM 复用 POI Grounding + Navigable Areas 训练中学到的视觉定位和可通行性判断能力。

### ABot-N1 的 Slow VLM 训练

ABot-N1 的 Slow VLM 做的精修与 Planner 不同：它不处理 AMap 粗坐标，而是对**已经精修过的局部目标**做像素级二次定位——输出 affordance pixel 和 target pixel。训练数据来自 **30M 样本异构预训练 + GRPO 后训练**。

**（一）Point-Goal — 2.36M 慢系统样本**

| 维度 | 说明 |
|---|---|
| 训练目标 | 给定三视角 RGB 和目标坐标 (dx, dy)，输出 affordance pixel |
| GT 制作方法 | **3DGS 投影** |
| 具体流程 | 1. 在高保真 3DGS 重建场景中，已知机器人当前位姿和目标点的 3D 坐标 <br> 2. 取前方 3m（室内）或 5m（室外）路径上的 3D 点 <br> 3. 通过已知的相机内外参，将该 3D 点投影到当前前向图像上 <br> 4. 投影得到的像素坐标 = GT affordance pixel |
| 为什么这样可行 | 3DGS 场景中所有几何信息已知，相机位姿已知，投影是精确的解析计算 |

GT 制作示意：

```
3DGS 场景中:
  机器人当前位置: (0, 0, 0)
  A* 路径上下一个 waypoint: (2.8, 0.5, 0) ——前方约 3m
        ↓
投影到前向相机图像平面:
  已知: 相机内参 K, 外参 [R|t]
  pixel = K · [R|t] · (2.8, 0.5, 0)
        ↓
GT affordance pixel: (u=612, v=348)
```

**（二）Instruction-Following — 5.11M 慢系统样本**

| 维度 | 说明 |
|---|---|
| 训练目标 | 给定三视角 RGB + 自然语言指令，输出 affordance pixel + target pixel |
| GT 制作方法 | **子指令端点投影 + 大模型蒸馏** |
| 具体流程 | 1. Qwen-3.5-27B 将长指令拆分为子指令，每段标注终点 <br> 2. 子指令终点在 3DGS/R2R 场景中的 3D 坐标已知 <br> 3. 投影到对应帧的图像上 → GT affordance/target pixel <br> 4. 同时，Qwen-3.5-27B 生成的子指令文本作为训练输入 |
| CoT GT | Qwen-3.5-27B 同时生成推理链文本（如"前方 50m 为路口，需要右转"），作为 CoT 的 GT |

**（三）POI-Goal — 3.0M 慢系统样本（仅训练慢系统）**

| 维度 | 说明 |
|---|---|
| 训练目标 | 给定街景图像，判断 POI 是否可见，若可见则输出入口 pixel |
| GT 制作方法 | **街景对蒸馏 + Wan2.1 视频生成 + A\* 轨迹投影** |
| 具体流程 | 1. 从 31M 街景图像对中筛选，蒸馏出 8M 正样本（POI 入口可见）+ 0.5M 负样本（不可见） <br> 2. 正样本：使用 Qwen-VL-Max 标注入口像素坐标 <br> 3. Wan2.1-I2V 将街景图生成为第一人称行走视频 <br> 4. A\* 规划从起点到 POI 入口的路径 <br> 5. A\* 路径的每一帧，将入口 3D 坐标投影到画面上 → GT target pixel |
| 负样本作用 | 训练模型判断"POI 不在画面中"，避免错误地将其他物体误认为目标 |

POI-Goal GT 制作流程：

```
31M 街景图像对 (起点 → POI 入口)
        ↓
筛选: Qwen-VL-Max 判断入口是否可见
  ├── 可见 (8M) → 标注入口像素 (u, v) → GT target pixel
  └── 不可见 (0.5M) → 标记为负样本
        ↓
Wan2.1-I2V 视频生成: 将街景图 → 第一人称行走视频
        ↓
A* 路径规划 + 投影: 每一帧的 affordance pixel GT
```

**（四）Object-Goal — 110K 慢系统样本**

| 维度 | 说明 |
|---|---|
| 训练目标 | 在图像中找到目标物体，输出 target pixel |
| GT 制作方法 | **数据飞轮 + 教师模型蒸馏** |
| 具体流程 | 1. 用已有的检测/VLM 模型在场景中标注目标物体的像素位置 <br> 2. 生成 CoT 推理链（"目标在画面右上角，被部分遮挡"） <br> 3. 人工或 VLM 校验一致性 <br> 4. 随机掩码三个上游信号（视觉/语言/坐标），防止模型过拟合单一模态 |

**（五）GRPO 后训练 — 像素目标精调**

预训练后的 Slow VLM 能大致预测像素目标，但缺乏安全边距。GRPO 后训练在以下三个维度进一步优化：

| 奖励项 | 作用 | GT 来源 |
|---|---|---|
| R_format | 输出格式是否符合 JSON schema | 规则检查 |
| R_target | 预测像素与 GT 像素的 L2 距离 | 3DGS 投影的真值像素 |
| R_safety | 反投影到世界坐标后，到最近不可通行区域的距离 | 3DGS 场景中的可通行性标注 |

GRPO 训练集按安全距离分三个区域采样（Safe : Critical : Danger ≈ 5 : 3 : 2），让模型在易、中、难三种场景下都学会安全预测。

### 两套系统 GT 数据制作的本质差异

| 维度 | ABot-N0 Planner | ABot-N1 Slow VLM |
|---|---|---|
| **VLM 要学什么** | "高德坐标对应画面里哪个位置"（AMap→pixel） | "精修后的局部目标对应画面里哪个位置"（坐标/指令→pixel） |
| **GT 的核心来源** | 街景图像 + VLM 自动标注 + 人工校验 | 3DGS 场景中的精确 3D 投影 |
| **GT 精度** | 像素级，但 VLM 自动标注有噪声（0.5M POI Grounding 需人工校验） | 亚像素级，3DGS 场景中投影是解析计算，无噪声 |
| **数据规模** | 5.0M（6 类推理数据，其中 3.0M 与精修直接相关） | ~13.6M 慢系统样本（五大任务合计） |
| **是否需要 3DGS** | 否（主要靠真实街景+VLM 标注） | 是（3DGS 是 pixel GT 的核心来源） |
| **人工标注量** | 高（Navigable Areas 1.2M 人工标注多边形） | 中（POI-Goal 31M 对 → VLM 筛选 → 人工抽样校验） |
| **后训练** | Planner 训练为 GenRewardModel，无单独的 pixel 精调 | GRPO 后训练：用 R_target + R_safety 精调 pixel goal 预测 |

---

### 关键结论

1. **ABot-N0 的 Planner VLM 精修能力是"训练出来的"而非 prompt 出来的**。它通过 General Reward Model 范式，在 POI Grounding + Navigable Areas + Instruction-Following 三类辅助任务上获得了视觉定位和可通行性判断能力。精修时不需要额外的 pixel 级 GT——Planner 的输出是一段新的子任务描述和目标坐标，不输出 pixel。

2. **ABot-N1 的 Slow VLM 精修能力是"端到端监督 + GRPO 强化"训练出来的**。它的 GT 主要来自 3DGS 场景中的精确投影——因为场景几何和相机位姿完全已知，投影是解析计算、无噪声的。这是 ABot-N1 能输出亚像素级精确 pixel goal 的基础。

3. **GT 制作成本差异巨大**。ABot-N0 的 Planner 依赖大量人工标注（1.2M 可通行区域多边形），ABot-N1 的 Slow VLM 依赖大量 3DGS 重建（800+ 室内 + 22 个室外场景）。前者是标注成本，后者是重建成本——如果已有 3DGS 资产，ABot-N1 的数据飞轮可以近乎零成本扩展。


---

## DualVLN 能否做复杂导航任务

DualVLN 的设计定位与前三个系统不同：它是围绕**单次 VLN episode** 设计的双系统基础模型，论文中主要验证的是 R2R/RxR 级别的室内指令跟随。但从架构上看，它的 System 2（VLM 全局规划器）可以被扩展为复杂导航的规划器，只是原论文没有做这一步。

### DualVLN 的原生能力边界

| 能力 | 是否具备 | 说明 |
|---|---|---|
| 单次 VLN episode（R2R/RxR 级别） | ✅ | 论文主要验证场景 |
| 理解复杂自然语言指令（多路标） | ✅ | System 2 做 image-grounded 推理 |
| 动态避障（行人） | ✅ | Social-VLN benchmark，领先 StreamVLN |
| 零样本 sim-to-real 迁移 | ✅ | VLN-CE 训练 → VLN-PE 物理执行 |
| 360° 全向感知 | ✅ | 双鱼眼 180° 全景输入 |
| 多段子任务拆解 | ❌ | 无内置 Planner，不拆解长程任务 |
| AMap/GPS 集成 | ❌ | 无全局路由能力 |
| 长期记忆（跨 episode） | ❌ | 无 Topo-Memory 或 Evidence Notebook |
| 失败恢复（跨段重规划） | ❌ | 单 episode 内无重规划机制 |
| 10km 级户外导航 | ❌ | 训练数据以室内为主 |

### DualVLN 如果要做"10 公里到示例咖啡店"，缺什么

如果把 DualVLN 放进前面 0.6 节的场景，它的 System 2 + System 1 架构需要以下扩展：

```
原版 DualVLN（单 episode VLN）:
  System 2 (VLM) 接收: 全景 RGB + "去厨房，经过客厅，在红色沙发旁停下"
  → 输出: mid-term waypoint pixel goals
  → System 1 (Diff-T) 执行

需要扩展为（多段户外导航）:
  外部 Orchestrator
    ├── 高德路径 → 分段 → 逐段喂入
    ├── 每段格式: {全景RGB + 分段指令 + 目标坐标}
    └── 段间切换和失败判断
          ↓
  DualVLN 执行单段:
    System 2 (VLM) 接收: 全景 RGB + "沿人行道走到前方路口右转"
    → 输出: mid-term waypoint pixel goals
    → System 1 (Diff-T) 执行 → 到达段终点
```

需要补齐的三个模块：

1. **外部分段调度器**：DualVLN 本身无 Planner，需要一个外部 Orchestrator 来做 AMap 交互 + 路径拆分 + 段间切换——和 ABot-N1 一样。

2. **户外训练数据**：DualVLN 的训练数据以 VLN-CE（室内 R2R/RxR）为主。要做户外长距离导航，需要补充户外 VLN 和 PointNav 数据，否则 System 2 的 VLM 不认识人行道、斑马线、路口等户外场景。

3. **长期记忆**：DualVLN 没有跨 episode 的记忆机制。如果要在 10km 过程中记住"刚才那个路口施工绕行了"，需要一个外部记忆模块（类似 ABot-N0 的 Topo-Memory 或 Qwen-RobotNav 的 Evidence Notebook）。

### 四个系统的"复杂任务能力"总览

| 维度 | ABot-N0 | ABot-N1 | Qwen-RobotNav | DualVLN |
|---|---|---|---|---|
| **内置 Planner** | ✅ Agentic Planner (VLM) | ❌ 需外部 Orchestrator | ✅ Planner (LLM, Qwen3.6-Plus) | ❌ 需外部 Orchestrator |
| **拆解粒度** | 细（20~30 段） | 取决于 Orchestrator | 中（8~12 段） | 取决于 Orchestrator |
| **记忆机制** | Topo-Memory 四层 | 无 | Evidence Notebook | 无 |
| **失败恢复** | Self-Reflector 闭环 | Orchestrator 开环 | Planner 半闭环 | Orchestrator 开环 |
| **对 AMap 的支持** | ✅ 原生集成 | ❌ 依赖 Orchestrator | ✅ Planner 集成 | ❌ 依赖 Orchestrator |
| **单段内视觉推理质量** | 中（Brain 直接出航点） | 高（Slow VLM pixel goal + CoT） | 中（LLM 骨干理解指令） | **高**（System 2 image-grounded 推理 + 显式-隐式双目标） |
| **动态避障** | 依赖 SAFE-GRPO + Neural Controller | 依赖 Fast VLA 局部绕行 | 依赖 Planner 切换 Safety 模式 | **✅ Social-VLN 原生支持** |
| **sim-to-real** | 需要 Neural Controller 适配 | Fast VLA 直接输出航点 | 需要底层控制器 | **✅ 零样本 VLN-CE → VLN-PE** |
| **户外能力** | ✅ 五任务含户外 | ✅ 五任务含户外 | ✅ PointNav + VLN 模式 | ❌ 训练数据以室内为主 |
| **系统复杂度** | 最高 | 低（模型侧简单） | 中 | 低-中（模型侧简单） |

### DualVLN 对本方案的独特价值

DualVLN 有两点是前三个系统不具备或做得不够好的：

1. **显式 + 隐式双目标表示**：System 2 同时输出显式 pixel goal（可解释）和隐式 latent feature（信息更丰富）。这避免了 ABot-N1 中纯 pixel goal 可能导致的信息瓶颈——如果 pixel goal 不够精确，隐式特征可以兜底。

2. **Social-VLN 动态避障**：DualVLN 是四个系统中唯一在论文里系统评估了动态行人避障的，前三个系统的避障更多依赖安全控制器/Neural Controller 而非 VLA 模型本身。这意味着 DualVLN 的 System 1 可以作为本方案 Fast VLA 的一个有力候选——它本来就支持动态避障。

因此，本方案中 Fast System 的候选可以有两种：
- **方案 A**：ABot-N1 的 Fast VLA（2B VLM 或 306M DiT），以 pixel goal 驱动，简单直接。
- **方案 B**：DualVLN 的 System 1（Diff-T Policy），同时利用 pixel goal + latent feature，天然支持动态避障。

### 一句话总结

**DualVLN 不能独立完成"10 公里到示例咖啡店"——它和 ABot-N1 一样，需要外部 Orchestrator 做分段调度。但它在单段内的视觉推理质量（双目标表示）和动态避障能力（Social-VLN）上是最强的。** 如果后续把它的训练数据扩展到户外场景并补齐 Planner 层，DualVLN 的架构最接近本方案"Slow-Fast 双系统 + 外部 Planner"的理想形态。


## ABot-N1 的外部 Planner 到底是什么

这是一个很容易产生的误解：0.3 节和 0.6.3 节反复提到 ABot-N1 "依赖外部 Orchestrator 做任务拆解"，但没有说这个 Orchestrator 是什么。

**事实是：ABot-N1 的论文没有定义外部 Planner。它不是"用了某个模型但没写清楚"，而是"架构上就没有这一层"。**

### 论文说了什么

ABot-N1 论文的核心贡献是 Slow-Fast 双系统架构和 pixel goal 统一接口。它的系统边界如下：

```
ABot-N1 的系统边界:
  ┌─────────────────────────────────────────┐
  │               ABot-N1                   │
  │                                         │
  │  Slow VLM (4B)                          │
  │   输入: 三视角RGB + 历史帧 + 子任务目标   │
  │   输出: CoT + Affordance Pixel + Target Pixel │
  │           ↓                             │
  │  Fast VLA (2B / 306M DiT)               │
  │   输入: RGB + CoT + Pixel Goal + 任务目标 │
  │   输出: 5 个 SE(2) 航点                  │
  └─────────────────────────────────────────┘
         ↑                        ↓
    子任务目标              5 个航点 → 控制器
    (谁生成？论文没说)
```

论文的九、与 ABot-N0 的对比一节明确写了：

> N1 没有保留 N0 中那个独立的 Agentic Navigation System
> N1 把 N0 的"规划器 + 拓扑记忆 + 执行器"三层架构压缩成了"慢思考 VLM → 像素目标 → 快 VLA 控制"的端到端双系统

这意味着 ABot-N1 的 **Slow VLM 只做 deliberative reasoning（看图决定下一步往哪走），不拆解子任务**。论文没有为 ABot-N1 配备 Planner，因为论文要证明的是"不需要 Agentic 系统，光靠 pixel goal 接口就能做五任务"。

### 部署时外部 Planner 是什么

论文没有给出答案，但可以从 ABot-N1 的实际部署环境——高德"涂涂"机器人——推断：

| 可能的实现 | 依据 | 可能性 |
|---|---|---|
| **复用 ABot-N0 的 Agentic Planner** | ABot-N1 和 ABot-N0 同属 AMap CV Lab，涂涂机器人同时使用了 ABot 全栈技术 | 高 |
| **高德云端导航服务 + 简单规则** | 高德本身有成熟的路径规划和 POI 搜索能力，涂涂的云端调度可以直接复用 | 高 |
| **通用 VLM（如 Qwen3.6-Plus）做任务拆解** | 和 Qwen-RobotNav 的 Planner 思路一致，用一个独立 LLM 做拆解 + 调用 ABot-N1 | 中 |
| **人工预定义路径** | 演示/测试场景下，路径可能是预先设定而非实时规划的 | 低（不适用于量产） |

最可能的组合是：**高德云端路径规划 + ABot-N0 的 Agentic Planner（简化版）+ ABot-N1 的 Slow-Fast 双系统执行**。ABot-N0 的 Planner 本身是独立训练的 General Reward Model，可以直接拿来用，只是不再需要 Topo-Memory 和 Self-Reflector 的那一套闭环。

### 为什么论文不定义外部 Planner

这是有意为之的设计选择，不是遗漏：

1. **架构解耦**：ABot-N1 要证明"pixel goal 是通用的跨任务接口"。只要外部系统把子任务描述成"一个目标 + 一段指令"，ABot-N1 就能执行。至于这个子任务是谁生成的——可以是 LLM、可以是高德 API、可以是人工、可以是另一个 VLA——ABot-N1 不关心。**不定义 Planner 恰恰说明接口的通用性。**

2. **学术聚焦**：论文的核心贡献是 Slow-Fast 架构和 pixel goal，不是 Agentic 系统。加上一个 Planner 会分散焦点，也会让消融实验更难做——你无法区分精度提升是来自 Slow-Fast 还是 Planner。

3. **工程灵活**：不绑定特定的 Planner，意味着部署时可以根据场景选择。云端可以用最强的 VLM，边缘可以用轻量 LLM，甚至可以多级 Planner（云端做全局、边缘做局部）。

### 对本方案的启示

ABot-N1 "不定义外部 Planner"这件事本身就是一个重要的架构决策。它说明：

- **Planner 和执行器可以、也应该解耦**。Qwen-RobotNav 也做了同样的选择（模型作为被调用工具），这不是巧合，而是 VLA 导航系统走向工程化的共同趋势。
- **本方案中 Planner 层的选型是灵活的**。可以用 ABot-N0 的 Agentic Planner（完整的 Agentic 闭环）、可以用 Qwen3.6-Plus + 参数化接口（类似 Qwen-RobotNav）、也可以用一个更轻量的规则+LLM 混合系统——ABot-N1 不挑 Planner。
- **但这也意味着如果 Planner 没做好，ABot-N1 无法兜底**。ABot-N0 有 Self-Reflector 和 Topo-Memory 可以做失败恢复，ABot-N1 完全依赖外部系统来判断"这一段的执行是否成功"。

简言之：**ABot-N1 的外部 Planner 不是一个具体的模型，而是一个架构槽位（architectural slot）**。论文没有填这个槽位，但给出了填它的接口规范——子任务 = 目标坐标或语言指令 + 可选的 CoT 提示。


## 户外 VLN 数据采集方案：从手机绑狗到规模化流水线

前面的讨论都围绕模型架构，这一节回答最实际的工程问题：**训练数据怎么来**。

一种直观方案是"机器狗绑手机，跑高德，录语音播报"——思路完全可行，但直接录下来的高德播报不能直接当 VLN 训练数据，需要经过一条后处理流水线。下面从"最朴素方案"出发，逐层叠加，最终给出一条可落地的采集路线。

### 方案 A：手机绑狗 + 高德播报（最朴素）

**硬件：** 机器狗 + 手机支架 + 手机（开高德步行导航）。

**操作：** 操作员遥控机器狗沿高德规划的步行路线行走，手机同步播报高德语音导航。机器狗自身相机录制前向/侧向 RGB 视频，手机同时录屏。

**一次采集产出的原始数据：**

```
第 1 段（0m ~ 80m）:
  RGB 视频帧序列: [frame_001, frame_002, ..., frame_2400] (30fps × 80s)
  高德语音: "沿示例道路 A向西直行 500 米"
  高德画面: 屏幕截图序列

第 2 段（80m ~ 150m）:
  RGB 视频帧序列: [frame_2401, ..., frame_4500]
  高德语音: "前方 50 米右转进入示例道路 B"
  ...
```

**能直接得到什么：**

| 产出 | 质量 | 是否可直接训练 |
|---|---|---|
| 视觉观测序列 | ✅ 真实户外场景、真实光照 | ✅ |
| 粗粒度路径 GT（GPS 轨迹） | ⚠️ 手机 GPS 精度 ~3-5m | ❌ 需要 RTK 补精度 |
| 自然语言指令 | ⚠️ 高德播报是人类导向的 | ❌ 需要改写 |

**核心问题：高德播报 ≠ VLN 指令。** 举个例子：

| | 高德播报 | 需要的 VLN 指令 |
|---|---|---|
| 示例 1 | "前方 50 米右转" | "沿人行道走到前方路口，看红绿灯，绿灯时右转进入示例道路 B，注意避让右转车辆" |
| 示例 2 | "沿当前道路继续直行" | "沿人行道靠右直行，经过左手边的公交站后继续向前" |
| 示例 3 | "您已到达目的地附近" | "前方 10 米为示例咖啡店入口，位于商场一楼东南角，面对公交站" |

高德播报有三个系统性问题：
1. **不含路标**：不说"经过公交站""看到麦当劳"，只说距离和方向。
2. **不含安全信息**：不说"等红绿灯""注意车辆""走斑马线"。
3. **不含视觉锚点**：不说"目的地入口在商场东南角"。

**结论：方案 A 不能直接产出训练数据，但它是后续方案的基础——真实场景的视觉观测和粗粒度路径就是从这里来的。**

---

### 方案 B：手机绑狗 + 高德播报 + VLM 改写

在方案 A 的基础上，加一道 **VLM 后处理**：把高德播报改写成可训练的 VLN 指令。

**流程：**

```
机器狗行走采集:
  前向 RGB 视频 + 高德语音播报 + 高德屏幕截图 + RTK GPS 轨迹
        ↓
Step 1: 时间对齐
  将高德语音的时间戳与 RGB 帧对齐
  得到: {frame_1000, "前方 50 米右转"}
        ↓
Step 2: VLM 指令改写（核心）
  输入: {关键帧图像 + 高德播报文本 + 高德地图截图 + GPS 位置}
  VLM 输出: 完整的 VLN 指令
        ↓
Step 3: 人工抽检
  每 100 条抽检 5 条，修正明显错误
        ↓
最终训练样本:
  {RGB 帧序列, VLN 指令, GPS 轨迹 GT}
```

**VLM 改写的 prompt 设计：**

```
你是一个户外导航指令生成器。
给定:
1. 机器人当前看到的画面（前向 RGB 图像）
2. 高德播报原文: "{高德播报文本}"
3. 高德地图截图
4. 当前位置和路线信息

请生成一条机器人可执行的 VLN 指令，要求:
- 包含路标: 描述画面中可见的永久性地标（建筑、店铺、公交站、路口特征）
- 包含安全提示: 是否需要等红绿灯、过斑马线、注意车辆
- 包含行动指引: 沿什么走、在哪里转、往哪个方向
- 语言自然、简洁，不超过 60 字
- 和前后指令衔接顺畅

示例:
  高德原文: "前方 50 米右转"
  VLN 指令: "沿人行道走到前方路口，等绿灯后右转进入示例道路 B，
            右手边是中国银行，沿银行外侧人行道继续走"
```

**这个方案的核心成本在 VLM 推理**。一条 30 分钟的采集路线约产生 20~30 条高德播报，每条改写消耗一次 VLM 调用。按 Qwen3.6-Plus 级别的 API 成本，约 0.01~0.03 元/条，一条路线的改写成本不到 1 元。

**结论：方案 B 可以产出训练数据，但指令质量完全依赖 VLM 的改写能力。建议先用 50 条做人工精标，作为 VLM 改写的 few-shot 示例和最终评测基准。**

---

### 方案 C：手机绑狗 + 高德播报 + 人工精标（高质量小批量）

方案 B 可以大批量跑，但第一批训练数据建议走人工精标路线。

**流程：**

```
采集 10~20 条真实路线（覆盖不同场景: 商业街/小区/路口/公园/施工路段）
        ↓
人工标注员逐段标注:
  1. 看回放视频，把高德播报改写成 VLN 指令
  2. 标注每个指令的起止帧（指令从哪一帧开始、到哪一帧结束）
  3. 标注关键路标的像素位置（可选，用于后续 pixel goal 训练）
  4. 标注可通行/不可通行区域（人行道边界、车行道）
        ↓
产出 500~1000 条高质量 VLN 样本
```

这批数据的价值：
- 作为 VLM 改写（方案 B）的 few-shot 示例和评测集；
- 直接用于模型的前几轮训练，验证户外 VLN 的基本可行性；
- 发现高德播报的系统性缺陷，反馈给改写 prompt 设计。

**成本估算：** 按每条指令 3~5 分钟标注时间、标注员时薪 50 元，500 条约 40~80 小时、2,000~4,000 元。

---

### 方案 D：仿真 + VLM 自动标注（规模化主力）

真实采集受限于路线数量、天气、时间，规模化必须靠仿真。

**流程：**

```
Step 1: 高德路线采集
  从高德 API 批量获取城市步行路线（覆盖不同城市的典型街区）
  目标: 收集 500~1000 条真实路线，每条 500m~3km
        ↓
Step 2: 3DGS 场景重建 / 仿真环境匹配
  优先: 用已有 3DGS 场景（ABot-N0/N1 的 7,802 个场景中的户外部分）
  补充: 对关键路线做 3DGS 重建（手机/相机拍摄 → 3DGS）
  降级: 对无法重建的路线，用 CARLA/SocCity 仿真器近似
        ↓
Step 3: 轨迹合成
  在 3D/仿真场景中的可通行图上:
  - 采样起点和子目标点
  - A* 规划路径（强制走人行道）
  - 生成完美 GT 轨迹（坐标、朝向、时间戳）
  - 加入坐标漂移模拟 GPS 误差
        ↓
Step 4: 指令生成
  对每条合成轨迹:
  - 在关键决策点（路口、转弯、POI 附近）截取 RGB 帧
  - VLM 根据轨迹、地图和关键帧生成 VLN 指令
  - 可选: 风格迁移，模仿方案 C 人工精标的指令风格
        ↓
Step 5: 质量过滤
  - VLM 自检: 指令是否与轨迹一致
  - 人工抽检: 每 200 条抽 10 条
```

**规模预期：** 500 条路线 × 每条约 10~20 段子任务 = 5,000~10,000 条仿真 VLN 样本。

**优点：** GT 轨迹完美、可控性强、可批量生成。  
**缺点：** 仿真视觉质量不如真实采集，指令的"自然度"可能不如人工精标。

### 与 ABot-N0 / ABot-N1 数据采集的关系

这个三层金字塔方案并不是否定 ABot-N0/N1 已有的数据引擎，而是在它们的基础上做**户外 VLN 的专项补充**：

| 已有数据（来自 ABot-N0/N1） | 本方案补充 |
|---|---|
| 仿真 PointNav 轨迹（室内外基础移动） | 真实户外 VLN 指令（高德路线 + VLM 改写） |
| 街景 POI Grounding（0.5M 图像对） | 高德真实路线的连续视频 + 指令 |
| 互联网视频伪轨迹（城市行走 Vlog） | 手机绑狗的真实同步采集 |
| 3DGS 场景中的投影 GT | 真实 GPS 轨迹 + VLM 改写指令 |

本方案的增量在于：**把"高德播报"提升为"VLN 训练数据"**。这是 ABot-N0/N1 的数据引擎没有覆盖的——它们有 POI 定位、有可通行区域、有仿真轨迹，但没有"真实高德路线上的真实 VLN 指令"。

## 户外导航数据采集方法全景

前文以"手机绑狗"为主线展开，这一节把所有可用的采集方法按类别列全，每类说明它的操作方式、能产出什么数据、以及局限性。你可以按需要选几类组合。

## 采集思路打开：不一定用机器狗

数据采集方法覆盖了 16 种方法，其中只有 3 种（手机绑狗、遥操作、骑行采集中的机器狗版）真正用到了机器狗。**其余 13 种都不需要机器狗。**

这一节的核心理念：**数据采集的载体和模型最终部署的载体可以是两个完全不同的东西。** 训练数据只关心三件事——传感器有没有配齐、视角能不能对齐、场景是不是真实——至于传感器装在一只 20 公斤的四足机器人上，还是装在一根自拍杆上，模型不在乎。

#### 机器狗作为采集载体的真实成本

用机器狗做采集，表面上看"最接近部署场景"，但实际代价很高：

| 成本项 | 说明 |
|---|---|
| 硬件成本 | 一台四足机器人（如 Go2）约 2~3 万元 |
| 出勤率 | 续航约 1~2 小时，每天有效采集时间不足 3 小时 |
| 场地限制 | 不能进商场、不能上台阶、不能坐地铁去下一个采集点 |
| 操作复杂度 | 需要经过培训的操作员，一人勉强、两人最好 |
| 充电/维护 | 每天需要充电，定期维护关节和传感器 |
| 运输 | 需要车辆运输到采集地点 |

结论：**机器狗是部署载体，不是高效的采集载体。** 把机器狗当采集工具，相当于让一台叉车去跑快递——能做，但很不划算。

#### 采集载体的核心要求

训练数据真正需要的是：

1. **RGB 相机**（前向 + 侧向，最好三视角）：分辨率 ≥1080p，帧率 ≥15fps。
2. **RTK GPS**（或高精度定位）：厘米级轨迹 GT。
3. **IMU**（9 轴）：朝向、加速度，用于运动补偿和姿态估计。
4. **时间同步**：所有传感器的时间戳可对齐。

只要这四个条件满足，载体是什么不重要。

#### 可选的采集载体

| 载体 | 硬件方案 | 单次覆盖距离 | 视角高度 | 日均产出 | 单次成本 |
|---|---|---|---|---|---|
| **手持自拍杆** | 手机（RGB+GPS+IMU+高德）+ 外置 RTK | 1~5 km | ~1.2m（成人手举） | 3~5 条路线 | ~50 元（交通+餐费） |
| **胸戴/头戴 GoPro** | GoPro（RGB）+ 手机（高德+GPS+IMU）+ RTK | 1~10 km | ~1.5m（成人眼高） | 5~8 条路线 | ~50 元 |
| **自行车/电动车** | GoPro 车把固定 + 手机 + RTK | 10~50 km | ~1.4m | 10~20 条路线 | ~80 元（含车辆） |
| **背包式采集设备** | 定制背包装相机阵列 + RTK + 电池 | 1~5 km | ~1.5m | 5~10 条路线 | ~100 元（设备折旧） |
| **汽车（副驾驶视角）** | GoPro 吸盘固定 + 手机 + RTK | 50~200 km | ~1.3m | 20~50 条路线 | ~200 元（含油费） |
| **机器狗** | 机载相机 + RTK + 手机 | 1~3 km | ~0.4m（地面视角） | 2~3 条路线 | ~500 元（设备折旧+操作员） |

#### 视角高度的差异处理

机器狗视角（约 0.4m）和采集载体视角（约 1.2~1.5m）有差异，但这个差异是可以通过训练处理的：

| 处理方法 | 说明 |
|---|---|
| **数据增强** | 训练时对图像做随机裁剪、平移、缩放，模拟不同高度和角度的变化 |
| **混合训练** | 同时用机器狗视角（少量，~10%）和高视角（大量，~90%）训练，模型学习不变表征 |
| **相机标定补偿** | 通过内外参将高视角图像投影到机器狗视角，做视角归一化 |
| **分阶段训练** | 先用高视角数据做预训练，再用少量机器狗视角数据做微调 |

ABot-N1 在实验中验证了这种做法：它在仿真数据（任意视角）上做预训练，在真实的机器狗视角数据上做微调，最终可以部署到四足机器人上。

#### 推荐的采集组合

**第一阶段（极低成本，单人即可）：**

| 方法 | 载体 | 日均产出 | 月投入 |
|---|---|---|---|
| 可穿戴相机 + 高德 | 胸戴 GoPro + 手机 | ~5 条路线/天 | ~1,500 元（交通+餐费） |
| 骑行采集 | 自行车 + GoPro + 手机 | ~15 条路线/天 | ~2,500 元 |
| 高德 API + 街景 | 无（纯 API） | ~200 条路线/天 | ~200 元（API 费用） |

个人操作员，一个月 20 个工作日，可以产出约 400 条真实路线 + 4,000 条 API 路线。**总花费不到 5,000 元，不需要任何机器狗。**

**第二阶段（小团队）：**

- 2~3 人，分头采集。一个人负责商业区步行路线、一个人负责骑行覆盖长距离、一个人负责 API 和仿真数据。
- 一个月可以产出 1,000+ 条真实路线 + 10,000+ 条 API/仿真路线。
- 总花费约 2~3 万元（人力+交通+设备折旧）。

**第三阶段（规模化）：**

- 外包给众包采集团队（类似高德/百度地图采集车的外包模式）。
- 或与配送/物流公司合作，在他们的运营车辆上挂载相机。

#### 一句话

**把机器狗留给部署和测试，把数据采集留给手机和 GoPro。** 传感器配全了，什么载体都能产出训练数据。

#### 一、基于高德 API 的方法（不需要手机绑狗）

**1.1 高德步行路径 API → 街景图像匹配**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 调用高德步行路径规划 API，输入起点和终点，拿到完整的 waypoint 序列（含经纬度、距离、转向指令） <br> 2. 对每个 waypoint，调用高德街景 API 或百度街景 API，获取该位置的 360° 全景图 <br> 3. 用 VLM 对全景图 + 高德指令做改写，生成 VLN 指令 |
| 产出 | VLN 训练样本：{全景图/街景图, VLN 指令, GPS 轨迹} |
| 优点 | 不需要硬件、不需要实地采集、一天可以覆盖数百条路线、成本极低 |
| 缺点 | 街景是离散的（每 10~50m 一张），不是连续视频；街景更新时间不定，可能与实际路况不符 |

**1.2 高德步行路径 API → 仿真环境复现**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 高德 API 获取 waypoint 序列 <br> 2. 在 CARLA / SocCity / 自建 3DGS 场景中，沿 waypoint 序列生成仿真轨迹 <br> 3. 在仿真环境中渲染 RGB 观测，生成连续视频 <br> 4. VLM 对关键帧 + 高德指令做改写 |
| 产出 | VLN 训练样本 + PointNav 轨迹（带完美 GT 航点） |
| 优点 | GT 轨迹完美、可以批量生成、不受天气/时间限制 |
| 缺点 | 仿真视觉质量受限，场景覆盖取决于仿真资产 |

**1.3 高德 POI 搜索 API → POI 入口数据**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 调用高德 POI 搜索 API，按类别（餐饮/零售/交通/医疗等）批量导出 POI 名称和坐标 <br> 2. 对每个 POI，获取其周边街景图像 <br> 3. VLM 标注入口像素位置 + 判断入口是否可见 <br> 4. 正样本（入口可见）+ 负样本（入口被遮挡/不在画面中） |
| 产出 | POI-Goal 训练数据：{街景图, POI名称, 入口像素坐标 或 不可见标记} |
| 优点 | 可以批量生成，覆盖海量 POI |
| 缺点 | 入口像素坐标依赖 VLM 标注精度，需人工抽检 |

**1.4 高德实时路况 API → 动态上下文**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 定时拉取高德实时路况数据（施工、拥堵、封路） <br> 2. 对有路况事件的路线，生成"需要绕行"的变体指令 |
| 产出 | 带异常场景的 VLN 指令（"前方道路施工，需要从左侧人行道绕行"） |
| 优点 | 覆盖真实的路况变化，增加指令多样性 |
| 缺点 | 需要长期持续采集，路况事件不可控 |

#### 二、真实采集方法（需要出外场）

**2.1 手机绑狗 + 高德播报**（0.11 节方案 A/B 已详述，此处不展开）

**2.2 遥操作 + 人工语音标注**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 操作员遥控机器狗沿预设路线行走 <br> 2. **同时用麦克风实时口述导航指令**（"前方路口右转，注意左边来车"） <br> 3. 录音和 RGB 视频通过时间戳对齐 |
| 产出 | 高质量 VLN 样本：指令自然、包含实时场景判断 |
| 优点 | 指令质量极高（人工实时生成，包含画面中的具体细节），直接对标方案 C 金标 |
| 缺点 | 操作员需要经过培训，效率低，一天只能产 10~20 条 |

**2.3 双人协作采集**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 操作员 A 遥控机器狗 <br> 2. 操作员 B 跟在后面，手持手机跑高德 + 口述补充指令 <br> 3. 操作员 B 同时用另一台设备拍摄第三人称视角（用于后续标注参考） |
| 产出 | 同 2.2，但效率和一致性更高（操作员 A 专注驾驶，B 专注标注） |
| 优点 | 分工降低认知负荷，指令质量更稳定 |
| 缺点 | 需要两人同时出外场 |

**2.4 可穿戴相机采集（不依赖机器狗）**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 采集员佩戴胸戴 GoPro / 头戴相机 <br> 2. 手持手机开高德步行导航 <br> 3. 正常步行经过路线，GoPro 录像 + 手机录屏 |
| 产出 | 第一人称步行视频 + 高德播报 |
| 优点 | 不需要机器狗，成本极低，一个人就能完成；可以覆盖机器狗进不去的地方（狭窄通道、台阶） |
| 缺点 | 第一人称视角高度和机器狗不同，需要做视角适配；步行速度和机器人不同 |

**2.5 骑行采集（覆盖长距离）**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 采集员骑自行车/电动车，车头绑手机（开高德）+ 运动相机 <br> 2. 沿高德骑行路线行走 <br> 3. 重点：在路口、POI 附近减速或停下，拍摄详细画面 |
| 产出 | 长距离（5~20km）路线数据，适合覆盖机器狗难以一天走完的长路线 |
| 优点 | 覆盖范围大、效率高 |
| 缺点 | 骑行视角和步行/机器狗视角差异大；速度不匹配导致动态障碍物表现不同于真实 |

#### 三、互联网/公开数据

**3.1 第一人称城市行走视频（B站/YouTube/抖音）**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 爬取"城市漫步""街区步行""街头第一视角"等关键词的第一人称视频 <br> 2. 过滤：稳定的步行视角、无明显剪辑、时长 >5min <br> 3. 用 SLAM / 3D 重建恢复相机轨迹 <br> 4. 用 VLM 反推导航指令（"如果我从视频起点走到终点，高德会怎么播？"） |
| 产出 | 伪 VLN 样本：{视频帧序列, 推断的VLN指令, 重建轨迹} |
| 优点 | 海量免费数据源，覆盖全球城市 |
| 缺点 | 轨迹精度依赖重建算法；没有高德路线对应关系；版权风险 |

**3.2 街景全景图（高德街景 / 百度街景 / Google Street View）**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 沿高德路线，每隔 10~20m 拉取一张街景全景图 <br> 2. 全景图拼接成"伪视频"（帧间插值或直接 frame-by-frame） <br> 3. VLM 对关键帧生成导航指令 |
| 产出 | VLN 样本（离散帧，非连续视频） |
| 优点 | 覆盖几乎所有城市道路，不需要实地采集 |
| 缺点 | 非连续视频，帧间变化不自然；更新频率不确定 |

**3.3 社交媒体地理标记图片**

| 维度 | 说明 |
|---|---|
| 操作方式 | 1. 从小红书/微博/Instagram 按地理位置标签爬取户外图片 <br> 2. 筛选带有明显 POI、路口、路标的图片 <br> 3. 用 VLM 为每张图片补充"如果是导航，当前该说什么" |

## 整体技术方案

### 系统概览：三层云边协同

```
用户指令（"带我去静安寺地铁站6号口"）
                ↓
[第1层] 云端 Agentic Planner
  高德POI查询 → 步行路径规划 → VLM任务分解
  → 分段子任务 {目标坐标 + 语义指令 + 观察配置}
                ↓
[第2层] 边缘 VLA 导航模型
  Slow System (4B VLM, ~1Hz)
    → CoT推理 + 像素目标 (affordance pixel + target pixel)
  Fast System (2B VLA / 306M DiT, ~10Hz)
    → 5~8个 SE(2) 局部航点
                ↓
[第3层] 安全控制器 + 机器人执行
  Neural Controller (10Hz+) → 机体速度 (v_x, v_y, ω)
  安全约束: 禁止进入车行道 | 斑马线等待 | 紧急停止
```

### 第 1 层：云端 Agentic Planner

来源融合：ABot-N0 的 Agentic Planner + Topo-Memory；Qwen-RobotNav 的 Planner + 证据笔记本。

**输入：**

- 用户自然语言指令（语音或文本）。
- 当前 GPS 位置（粗定位，米级精度）。
- Topo-Memory（历史已知 POI、可达性记录）。
- 高德实时路况与电子围栏。

**输出：** 分段子任务序列，每段含：

- `mode`：VLN（指令跟随）或 PointNav（坐标移动）或 Safety（交通灯等待）。
- `goal_relative`：以当前机器人位姿为原点的局部坐标 `(dx, dy)`。
- `instruction`：自然语言导航指令。
- `obs_config`：由 Qwen-RobotNav 思路衍生的观察配置参数 `(γ, B, m)`。

**VLM 粗坐标精修：**

高德返回的路口中心点不能直接作为 PointNav 目标（不区分人行道/车行道）。Planner 收到来自边缘的当前画面后：

1. VLM 判断目标在画面中的可通行位置；
2. 通过单目深度估计投影为局部坐标 `(dx, dy)`；
3. 若无法从画面定位（遮挡/距离太远），转换为 VLN 语义指令。

### 第 2 层：边缘 VLA 导航模型

来源融合：ABot-N1 的 Slow-Fast + 像素目标接口；Qwen-RobotNav 的参数化观察；DualVLN 的显式-隐式双目标。

**Slow System（慢系统）**

- 基础：4B 参数多模态 VLM（Qwen3-VL 级别）。
- 频率：约 1 Hz。
- 输入：三视角 RGB + 历史关键帧 + 当前子任务目标 + 上次 CoT/像素目标。
- 输出：CoT 推理链 + Affordance Pixel（可通行方向）+ Target Pixel（目标在画面位置）。

**Fast System（快系统）**

- 版本一（研究）：2B VLM（Qwen3-2B），统一处理视觉、CoT 和像素目标。
- 版本二（量产）：306M DiT（Diffusion Transformer），轻量动作专家。
- 频率：10 Hz。
- 输入：当前三视角 RGB + 慢系统输出的像素目标/CoT + 任务目标。
- 输出：5~8 个 SE(2) 局部航点，每个含 `(x, y, cosθ, sinθ)`。

**异步推理：** 慢系统 1 Hz 更新像素目标，快系统 10 Hz 持续跟踪同一像素目标生成航点。两次慢系统更新之间，快系统使用缓存的 `(CoT, pixel_goal, ref_frame)`。

### 任务模式切换

继承 Qwen-RobotNav 的设计，同一模型支持多种调用模式：

| 模式 | 适用子任务 | Slow 输出 | Fast 输入增量 |
|---|---|---|---|
| VLN | 沿人行道走到路口 | CoT + affordance + target pixel | 语义指令文本 |
| PointNav | 直行 80m 到前方坐标点 | affordance pixel（无 target） | 相对坐标 |
| ObjNav | 到达 POI 入口 | CoT + target pixel（找到后） | 目标描述文本 |
| Safety | 斑马线等待 / 红灯停车 | affordance pixel = 原地位置 | 交通灯/行人检测信号 |

### 第 3 层：安全控制器

- Neural Controller（基于 CE-Nav）：以航点和 LiDAR 占用图为输入，输出机体速度，频率 ≥10 Hz。
- 社会合规约束：逐帧分割人行道/车行道边界；航点若落入车行道则强制 clip。
- 紧急停止：LiDAR/深度相机检测到 <0.5m 内障碍物时立即停止。

### 关键设计决策

| 维度 | 选择 | 理由 |
|---|---|---|
| 规划器位置 | 云端 | 长程分解和高德交互延迟可接受 |
| VLA 架构 | Slow-Fast 双系统 | ABot-N1 已验证五任务统一 |
| 观察策略 | 参数化可配置 | Qwen-RobotNav 解决多任务模式切换 |
| 动作表示 | 局部航点 5~8 个 | 平衡规划距离和控制精度 |
| 安全层 | 独立于 VLA | 安全不能依赖网络，须本地硬实时 |

### 失败恢复策略

| 失败情况 | 恢复方式 |
|---|---|
| 偏离人行道 | Fast system 即时纠偏；连续 3 步偏离则触发 slow 重推理 |
| 目标被遮挡 | 从 Topo-Memory 检索已知地标，用语义描述替代坐标 |
| 高德路径因施工关闭 | Planner 检测多次到达失败后请求高德重新规划 |
| GPS 丢失 | 切换到视觉里程计 + 已知路标定位 |
| 网络中断 | 边缘 Planner 缓存最近 3 段子任务，逐段执行 + 安全层兜底 |

## 数据集设计

整体借鉴 ABot-N0 的 16.9M 轨迹 + 5M 推理数据引擎和 ABot-N1 的 30M 多任务预训练。

### 数据类型与规模

| 数据类型 | 用途 | 目标规模 | 来源 |
|---|---|---|---|
| 户外 PointNav 轨迹 | 基础移动、避障 | 3M | 仿真 (2M) + 真实机器人 (0.5M) + 互联网视频 (0.5M) |
| 户外 VLN 指令跟随 | 语言驱动长程导航 | 2M | 高德路线 + Wan2.1 视频生成 + VLM 指令标注 |
| 社会导航 | 行人避让、交通规则 | 1.5M | SocCity 仿真 + 街景标注 |
| POI 入口到达 | 店铺/地铁口精确到达 | 1.5M | 街景 + Wan2.1 视频生成 + A* 轨迹 |
| 人跟随/导盲 | 跟踪、引导、社会距离 | 1.5M | 仿真 + 真实采集 |
| 推理数据 | 可通行区域、安全判断 | 3M | VLM 自动标注 + 人工校验 |
| **合计** | | **~12.5M** | |

### 户外 PointNav 采集

**阶段一：仿真采集（主力）**

- 环境：SocCity (~3.4 km²) + 自建城市 GIS 场景 + Habitat 户外。
- 轨迹生成：在可通行图上采样起点和目标点，A* 计算最短路径，强制走人行道。
- 加入坐标漂移恢复轨迹（GPS 误差 1~5m 偏移后回正）。
- 加入动态障碍（行人、自行车、外卖电动车）。
- 规模：2M 条。

**阶段二：真实机器人遥操作**

- 设备：四足机器人 + 三视角 RGB + RTK GPS + IMU。
- 场景：不同城市的典型街区、公园、校园。
- 规模：500K 条。

**阶段三：互联网视频伪标注**

- 爬取城市行走 Vlog，筛选第一人称行人视角。
- π3 稠密三维重建 + MoGe 尺度对齐 → 伪轨迹。
- 语义分割区分人行道/车行道，过滤车道部分。
- 规模：500K 条。

### 户外 VLN 指令采集

1. 从高德获取真实步行路径，拆分成长约 50~100m 的段落。
2. 从高德街景 / Google Street View 获取对应全景图。
3. Wan2.1 视频生成模型合成段落第一人称行走视频。
4. VLM（Qwen3.6-Plus 级别）根据路径和视频自动生成自然语言指令。
5. 人工抽样校验。

指令示例：

- "沿人行道往前走约 80 米，经过左手边的便利店"
- "到红绿灯路口右转，看到地铁站入口停下"

规模：2M 条。

### 社会导航数据

- 在 SocCity 中导出带车辆、行人的动态轨迹，强制社会合规约束。
- 生成 CoT 推理链："前方是红灯，需要停下""有行人从左侧接近，减速靠右"。
- 街景图片 + VLM 自动标注可通行区域多边形。
- 规模：1.5M 条。

### POI 入口到达数据

- 从高德 POI 库提取店铺、地铁口、公交站。
- 街景图片 + Wan2.1 视频生成 → A* 路径 → 入口 pixel 标注。
- 正负样本平衡：可达 vs 不可达（施工围挡、台阶、封闭入口）。
- 规模：1.5M 条。

### 部署校准集

- 128~256 张代表性户外场景图片。
- 覆盖白天/黄昏/夜间/雨天/逆光。
- 覆盖人行道/路口/商业街/公园/施工区。
- 包含动态障碍物。

## 部署硬件与内存预算

### 选型原则

- 降成本：去掉冗余传感器，保留核心且不可替代的。
- 降功耗：低功耗处理器和 Sensor Hub。
- 高可靠：工业级温度（-20~60°C），防水防尘 IP65+。
- 易组装：模组化，BOM 物料少。

### 传感器与计算平台

| 部件 | 可参考的技术路线 | 选型需要验证的条件 |
| --- | --- | --- |
| RGB 相机 | 前向或多视角相机 | 视野、曝光、同步、安装振动与训练视角一致性 |
| IMU 与里程计 | 惯性、轮式或腿式状态估计 | 时间戳、短程漂移和坐标系一致性 |
| GNSS / RTK | 户外绝对定位 | 遮挡、多径、差分服务和失锁降级 |
| 深度或 LiDAR | 局部几何与碰撞检查 | 近距盲区、雨雾、反光表面和功耗 |
| 通信模块 | 蜂窝网络或场地网络 | 时延、覆盖与断网时的本地行为 |
| 边缘计算 | Orin NX、AGX Orin 或 Thor 等 | 模型精度、显存峰值、持续时延、散热与电源 |

采购成本应按具体模组、载板、配件、币种和采购数量分别询价。不能将开发套件价、裸模组价与整机物料成本混用。

### 内存预算示例

仅按参数量估算，4B 模型的 INT8 权重约为 4 GB，306M 模型的 FP16 权重约为 0.6 GB。实际运行还需要视觉编码器、激活、缓存、推理引擎工作区与系统内存。能否在 16 GB 设备上共存，需要用完整管线测量峰值，不能只把权重相加。

### 配置演进

先在资源充足的平台验证闭环，再依据时延和功耗测量结果决定量化、模型裁剪、云边分配与传感器精简。每次硬件变更都应重新测试定位、碰撞检查和失效恢复。
