# LightNav-0：把 VLM 的空间智能“直接变成”通用导航

> **论文**：*LightNav-0: Eliciting VLM Spatial Intelligence for Generalist Embodied Navigation*  
> **作者**：Light Origins Team（Shaoan Wang 等 20 人）  
> **发布时间**：2026-08-31  
> **arXiv**：https://arxiv.org/abs/2608.30935  
> **GitHub**：https://github.com/lightorigins/LightNav-0  
> **模型**：LightOriginsHQ/LightNav-0  
> **License**：代码 Apache 2.0；EVT-Bench 本身为 CC BY-NC-SA 4.0，仓库未再分发

## TL;DR

LightNav-0 是一个 **4B 参数、单模型、单目 RGB** 的通用具身导航模型。它的核心思路不是继续给 VLM 加“导航专用预测头”，而是把 VLM 已经具备的空间理解能力，通过一个统一的 token 接口直接牵引到导航动作上：

1. **双通道 pointing token**：模型先输出“可走点”和“目标点”，把空间意图显式落到图像网格里；
2. **三级 RVQ 动作 token**：再用三个离散 token 解出 10 步 SE(2) 轨迹，交给机器人自己的底层控制器；
3. **时序感知的历史压缩**：视觉历史按照“越近越细、越远越粗”的方式压缩，控制上下文长度；
4. **ER mid-training → SFT → RL** 的训练路径，加上 2K+ 场景、4K+ 小时导航轨迹；这些轨迹主体来自 Real2Sim2Real 合成数据，真实/仿真小时数没有单独公开。

结果是：同一个 checkpoint，不做任何按基准微调，就能同时做指令导航、开放词汇物体导航和具身视觉跟踪；在多个公开 VLN/ObjectNav/EVT 基准上拿到 SOTA，并能跨机器人本体、跨场景做零样本真机部署。

## 一、它要解决什么问题

传统具身导航系统通常把问题拆成多个模块：

```
视觉感知 → 语义/地图表示 → 规划器 → 轨迹生成 → 底层控制
```

每个任务、每种机器人本体、每个环境，往往都要针对性地设计模块、定义接口、收集数据、重新训练。这样做的代价很高：换一个机器人，就要重做一遍动作空间适配；换一个任务，就要新增一套预测头；换一个环境，就要重新标定数据和专家轨迹。

LightNav-0 的切入点是：**现代 VLM 已经具备不错的视觉 grounding、空间推理和指向能力**。与其把这些能力拆散再重搭，不如直接“唤起”它们，并把导航任务也表达成同一个自回归 token 序列。

因此它的目标很明确：

- 不引入 task-specific head；
- 不引入 per-embodiment expert；
- 不靠任务分类 token 来区分任务；
- 所有任务共享同一套感知、推理和动作接口。

论文的说法是：任务语义完全来自自然语言指令，模型本身不需要知道“我在做 VLN 还是 ObjectNav 还是跟踪”。

## 二、方法：把导航变成一次 token 生成

### 2.1 基座：Qwen3-VL-4B-Instruct

LightNav-0 从 Qwen3-VL-4B-Instruct 初始化，并且**没有新增任何导航专用模块**：

- 没有 waypoint predictor；
- 没有 task-specific action head；
- 没有 per-embodiment expert；
- 只有词表被扩展了：新增 indexed pointing tokens 和 RVQ action tokens。

这意味着空间推理痕迹和动作码，都是通过原始 VLM 的自回归 LM head 解码出来的。整个模型仍是一个“视觉语言模型”，只是输出词表多了一组专门用于导航的符号。

这一点很重要。它把导航问题压缩成一个更接近预训练任务的生成问题，而不是在预训练模型旁边挂一个完全异构的策略网络。

### 2.2 双通道 pointing：显式空间意图

每个决策步，模型消费：

```
时间戳化的第一视角 RGB 历史 + 自然语言指令
```

然后先输出两类 pointing token：

1. **Affordance point（apos）**：一个可执行的前进方向或自由空间 waypoint；
2. **Object point（opos）**：任务目标所在的位置。

每个 point 使用一个图像网格 token 表示。模型不是直接从图像跳到动作，而是先在像素空间中“指出来”：

- 哪里可以走；
- 目标在哪里，哪怕当前不可见。

这种显式 spatial reasoning trace 的好处是：它把规划决策 grounded 到了图像里，也让同一套 token 接口可以服务于不同任务和不同场景。对于跟踪任务，`opos` 指向目标人物/物体；对于指令导航，`opos` 指向语言描述的目标位置；对于物体导航，`opos` 指向目标物体。

### 2.3 RVQ 动作 tokenizer：三个 token 生成一条轨迹

pointing 之后，模型再输出 **三个 RVQ action tokens**，对应未来 10 步的 SE(2) waypoint。

RVQ 是 Residual Vector Quantization 的缩写，即“残差向量量化”。一条连续轨迹先被粗量化，再逐步用残差修正。LightNav-0 的配置是：

| 量化层级 | 码本大小 | 分辨率量级 | 作用 |
|---|---|---|---|
| 第一层 coarse | 256 | ~0.9 m | 主干运动方向和大尺度形状 |
| 第二层 residual | 256 | ~7 cm | 进一步修正轨迹形状 |
| 第三层 residual | 256 | ~4 cm | 提供厘米级精细形状 |

这个设计有两个工程优点：

- **前缀可执行**：即使只解码出第一层 token，也能得到一条可执行的粗轨迹；
- **前缀可细化**：每增加一个残差层，轨迹精度更高。

所以三个 token 同时表达了“大方向”和“厘米级路径形状”，最终解码成 10 个 `[forward, lateral, yaw]` 形式的相对位姿。这个几何接口是 embodiment-agnostic 的，具体到轮式、四足、人形或无人机，只由各平台自己的底层控制器处理。

### 2.4 时序感知历史压缩：像遗忘曲线一样压缩历史

导航同时需要：

- 最近的精细几何信息，比如眼前的障碍物、台阶、目标框；
- 长时程上下文，比如“我刚刚经过了哪里”“之前的指令对应哪个方向”。

如果每一帧都按原分辨率编码，视觉 token 数量会随历史长度无限增长。LightNav-0 的做法是在 ViT 之后做历史压缩，遵循类似 **Ebbinghaus 遗忘曲线**的形状：

```text
帧越旧 → 采样率越低 → 空间池化步长越大 → token 越少、越粗糙
帧越新 → 采样率越高 → 空间池化步长越小 → token 越多、越精细
```

具体地说：

- **采样率**随帧龄指数下降；
- **空间池化 stride**随帧龄指数增长；
- 当前帧保留最细粒度；
- 时间戳 token 在池化后保持时间顺序。

压缩器在视觉 transformer 之后运行，并提供 256K、576K、1M 等可配置像素预算。这样既限制了上下文长度，又不会把整段历史塌缩成一个固定的低分辨率 summary。

这个设计是 LightNav-0 比较值得注意的工程细节之一：它把“记忆”做成了多分辨率、带时间衰减的流式表示，而不是简单的 ring buffer 或固定长度的视频 summary。

### 2.5 模型结构、参数量、输入与输出速览

如果只看“网络本体”，LightNav-0 并不复杂。它没有额外的导航大模块，结构如下：

| 模块 | 作用 | 是否新增导航专用模块 |
|---|---|---|
| Native-resolution ViT | 对采样出的历史帧逐帧编码，得到 patch grid | 否，来自 Qwen3-VL |
| Slow-Fast History Compressor | 在 ViT 之后按帧龄采样、池化，控制历史 token 总量 | 是 LightNav-0 的处理逻辑，但主要是采样/池化策略 |
| 36-layer causal LM | 接收交织后的视觉、时间戳、指令 token，自回归解码 | 否，来自 Qwen3-VL |
| Original LM head | 输出 extended vocabulary 中的 token | 否，只扩词表 |
| Dual-channel pointing decoder | 把 `<apos>` / `<opos>` token 映射回图像网格坐标或特殊状态 | 推理侧解码，不是预测头 |
| RVQ action tokenizer | 3 个 256-entry codebook，把 3 个 action token 解成 10 步 SE(2) 轨迹 | 确定性 decoder，不是神经网络预测头 |
| 机器人端 trajectory follower / low-level controller | 把轨迹转成平台速度/步态命令 | 不属于模型 |

#### 参数量

LightNav-0 从 **Qwen3-VL-4B-Instruct** 初始化，论文按 **4B** 这一档来报告。

关键点是：它没有增加 waypoint predictor、task head 或 per-embodiment expert。扩展词表会带来新增 token 的 embedding / LM-head 行，但网络主干的参数量仍然是 Qwen3-VL-4B 这一级别。

#### 输入

每个决策步的输入包括：

```text
natural-language instruction I
+ timestamped egocentric RGB history O_{1:t}
+ current observation o_t
```

这些内容会被组织成 **一个 causal sequence**。视觉历史经过 ViT 后再做 slow-fast 压缩，当前帧保留最细粒度，历史帧越旧越粗；时间戳 token 保留顺序。

模型只依赖 **单目 RGB**：

- 没有 depth；
- 没有 odometry；
- 没有全景图或多相机 rig；
- 不需要 task-identification token。

训练时通过 camera randomization 覆盖 FOV 90°–130°、高度 0.5–1.5 m、pitch -15°–15°。

#### 输出

每个决策步，模型输出固定长度的 token 序列：

```text
<apos_i>  <opos_j>  <act_L0_k0>  <act_L1_k1>  <act_L2_k2>
```

具体含义是：

| 输出 token | 含义 |
|---|---|
| `<apos_i>` | Affordance point：可行前进方向、自由空间 waypoint；特殊索引可表示原地左转/右转/停止 |
| `<opos_j>` | Object point：目标物体或目标位置；特殊索引可表示目标不可见 |
| `<act_L0_k0>` | 第一层 RVQ token，约 0.9 m 量级的粗轨迹 |
| `<act_L1_k1>` | 第二层 RVQ token，约 7 cm 量级的残差修正 |
| `<act_L2_k2>` | 第三层 RVQ token，约 4 cm 量级的精细修正 |

把三个 action token 送到 RVQ decoder 后，得到 **10 个未来 SE(2) waypoint**：

```text
[forward_m, lateral_m, yaw_rad] × 10
```

然后由机器人各自的 low-level controller 或 trajectory follower，转成实际速度、步态或飞控命令。服务端 API 层还会把它包装成 `actions.actions`、`stop`、`visible`、`pointing` 等字段。

这里有一个很简洁的设计：**pointing 是 latent spatial reasoning trace，动作只是三枚离散 token。** 因此模型不需要输出自由文本，也不需要为不同任务设计不同的输出头。

### 2.6 论文里展示了哪些任务和指令示例

LightNav-0 的能力主要覆盖三大类导航任务：**指令跟随、物体目标导航/搜索、具身视觉跟踪**。论文正文和图里出现过的具体例子大致可以全部归到下面这些。

#### 1）自然语言指令跟随

这类任务要求机器人理解一段自然语言路线，走到指定位置并停下。论文中的例子包括：

- “Walk down the hall, stop next to the brown chair.”  
  沿着走廊走，停在棕色椅子旁边。

- “Walk to the blue food menu sign next to the stone building.”  
  走到石楼旁蓝色的餐饮指示牌那里。

- “Exit the room, turn right. Turn right at stairs, enter bedroom, stop by the bed.”  
  离开房间右转；在楼梯处右转，进入卧室，停在床边。

这也对应 VLN-CE 的 R2R / RxR 指令导航评测。

#### 2）物体目标导航与开放词汇搜索

这类任务要求机器人根据物体类别或开放词汇描述找到目标。论文中的例子包括：

- “Find the plant outside the room.”  
  找到房间外面的植物。

- “Find the toilet.”  
  找到卫生间。

在 ObjectNav 评测里，还覆盖：

- MP3D、HM3D v1、HM3D v2 的封闭词表物体导航；
- HM3D-OVON 的开放词汇物体导航，包括 seen、synonyms、unseen 三类；
- 即使训练时没有见过某些类别名称，模型也要根据语言描述找到目标。

#### 3）具身视觉跟踪

这类任务要求机器人持续跟随一个动态目标，而不是到达某个固定地点。论文中的例子包括：

- “Track the man in blue.”  
  跟踪穿蓝色衣服的人。

- “Follow the person wearing a blue shirt and black pants.”  
  跟着穿蓝衬衫和黑裤子的人。

- “Follow the person in the red shirt.”  
  跟着穿红衬衫的人。（这是仓库 Quick Start 里的示例）

真机部署中，作者强调模型还能跟踪训练时没有见过的动态目标类别，包括：

- humanoid robots；
- wheeled robots；
- carts。

在 EVT-Bench 上则区分：

- STT：single-target tracking，单目标跟踪；
- DT：distracted tracking，有相似干扰物时的跟踪。

#### 4）INSIGHT-Bench 中的五类空间指令

INSIGHT-Bench 把目标指令进一步按“需要什么空间机制”分成五类：

| 指令类型 | 论文示例 | 中文意思 |
|---|---|---|
| Base | “Head to the sofa and stop next to it.” | 走到沙发旁停下 |
| Direction | “Head to the fire alarm to your left and stop next to it.” | 走到你左边的火警报警器旁停下 |
| Relation | “Find the sofa next to the fireplace and walk up to it.” | 找到壁炉旁边的沙发并走过去 |
| Extremum | “Go over to the leftmost table and wait there.” | 走到最左边那张桌子并等待 |
| Ordinal | “Walk straight over to the second chair from the left.” | 直走，到左边数第二把椅子 |

这五类覆盖了目标唯一性、方向、参照物关系、极值和序数等不同难度。

#### 5）跨游戏/跨域零样本例子

论文还用同一个 checkpoint 在完全不同的游戏域里做零样本测试：

- **CS 1.6**  
  “Turn left around the crates and follow the upper tunnel to the B-marked passage.”  
  绕过箱子左转，沿上方隧道走到 B 标记通道。

- **Minecraft**  
  “Follow the creeper and keep it centered.”  
  跟随苦力怕并让它保持在画面中央。

- **VizDoom**  
  “Turn right, then walk up the stairs to the blue-lit doorway.”  
  右转，然后上楼走到蓝光门口。

- **Trigger Rally**  
  “Keep the green checkpoint ring centered and drive uphill through it.”  
  让绿色检查点环保持居中，并穿过它上坡。

这些例子说明模型学到的“pointing + 轨迹”接口没有绑定在某一种视觉风格、场景结构或运动动力学上。

#### 6）真机与多机器人本体

论文和 README 还展示了真机上的任务：

- 在未见过公园中，人形、四足、轮式、无人机分别跟随语言指定的目标；
- 视觉跟踪、指令导航、物体搜索；
- 跟随人和机器人目标；
- 静态与动态目标。

对应机器人平台包括：

- LightBot-0 人形；
- Unitree Go2 四足；
- 自研四旋翼；
- LimX TRON 1 轮式。

所以总的来看，LightNav-0 不是“只能做一个任务”，而是把下面这些统一进同一个模型：

```text
自然语言路线导航
开放词汇物体搜索
单目标/干扰物视觉跟踪
跨场景、跨本体、跨域零样本导航
```

## 三、训练：先唤醒空间智能，再做导航对齐

### 3.1 LightNav-ER：第一阶段具身推理 checkpoint

LightNav-0 的训练先从一个 **embodied reasoning** 阶段开始。官方叫它 LightNav-ER，用于初始化后续导航模型。

它的意义是：在正式做导航动作对齐之前，先把 VLM 的 pointing、grounding、空间推理能力“唤醒”并校准到具身场景。

论文给出的完整集平均分如下：

| Model | Params | 8 项具身推理基准完整集平均 |
|---|---|---|
| Qwen3-VL | 4B | 63.1 |
| Qwen3.5-4B | 4B | 60.8 |
| Molmo2-ER | 8B | 62.8 |
| **LightNav-ER** | **4B** | **67.4** |

一个 4B 模型在完整集平均分上超过了 8B 的空间专用模型，这是它后续导航能力的重要前置条件。

### 3.2 数据总量：4K+ 小时导航语料，真实/仿真没有公开小时拆分

论文在 Section IV 给出的总口径是：

| 项目 | 论文中的数字 |
|---|---|
| 总导航训练语料 | **2K+ scenes / 4K+ hours of embodied trajectories** |
| 真实机器人导航轨迹小时数 | 未单独公开 |
| 仿真合成导航轨迹小时数 | 未单独公开 |

也就是说，**“真实数据多少小时、仿真数据多少小时”这个拆法，论文没有直接给**。4K+ 小时是导航轨迹总量，其中主体来自 Real2Sim2Real 的自动化数据合成管线：先把真实场景转成可复用仿真资产，再生成轨迹和语言指令。

如果换成“样本量”的口径，论文给了更细的构成：

| 数据阶段 | 样本量 |
|---|---|
| ER mid-training Stage I | 13.0M samples |
| SFT co-train 中的 ER/VQA rehearsal | 5.2M samples |
| SFT 总语料 | 23.2M samples |

在 SFT 的优化采样里，**77.6% 的样本带导航动作监督，22.4% 用来维持 ER/VQA 能力**。这种“一边学导航动作，一边复述感知与空间推理”的采样方式，是为了避免在导航对齐时把预训练模型的空间能力丢掉。

Fig. 6 还给出了 SFT 数据源的样本量构成：

| 数据源 | 样本量 |
|---|---|
| VQA | 5.2M |
| ObjectNav | 4.7M |
| SRDF | 4.7M |
| ScaleVLN | 2.8M |
| Tracking | 2.8M |
| VLN-CE RxR | 1.8M |
| VLN-CE R2R | 642K |
| INSIGHT-Bench | 454K |

这些来源覆盖了指令跟随、物体目标导航、开放词汇导航、具身视觉跟踪，以及更大规模的合成/自蒸馏路线数据。

### 3.3 详细拆解 Real2Sim2Real

LightNav-0 的数据策略，官方称之为 **Real2Sim2Real**。论文里对应的是“Simulation-based Data Engine”，也就是图 1 最左侧的数据引擎。

它的核心逻辑不是“只采真实机器人数据”，也不是“只做纯仿真”，而是把真实世界当作**任务和场景的分布来源**，把仿真当作**规模化生成训练轨迹的放大器**。

```text
Real ────────────────▶ Sim ────────────────▶ Real
真实室内外场景          可复用仿真资产          零样本真机部署
定义场景/任务分布       自动生成轨迹/指令        验证跨本体/跨场景
▲                                              │
└──────────── 失败与长尾回流，形成飞轮 ────────────┘
```

#### 第一步：Real，确定数据分布边界

官方 PR 说团队使用 **2000+ 个真实室内外场景** 作为源头。这里有一个重要但容易被误解的点：**论文正文列出的场景源主要是公开数据集**，例如 HM3D、MP3D、VLNVerse、Habitat-GS、InteriorGS，而不是在论文中另外公开一套由作者独立重新扫描的 2000 个场景。更准确的理解是，这些公开场景很多本身来自真实空间的扫描或重建，LightNav-0 主要把它们统一成可复用的仿真资产；官方 PR 的“2000+ real scenes”应理解为“真实场景来源的资产”，而不是“作者自采的 2000 个原始场景数据集”。

这里的关键不是直接把 2000+ 个场景全部拿去录真实机器人轨迹，而是让这些真实场景告诉数据管线：

- 真实世界中会有哪些室内布局、室外结构和视觉风格；
- 机器人在真实环境中会遇到哪些任务和语言指令；
- 哪些导航行为、失败模式是实际部署中真正会出现的。

#### 第二步：Sim，把真实场景变成可重复生成的数据资产

真实场景被转换为可复用的仿真资产，然后通过自动化管线规模化合成了 **4K+ 小时** 导航轨迹。这个过程把“真实数据的分布边界”变成“可采样、可变化、可泛化的训练数据”。

论文里具体做了 **camera randomization**：

- FOV：90°–130°；
- 相机高度：0.5–1.5 m；
- pitch：-15°–15°。

这意味着同一场景可以产生不同视角、不同高度、不同俯仰角的轨迹，减少模型对固定相机配置的依赖。

#### 从真实场景到可复用仿真资产，论文能确认的链路是：

LightNav-0 论文没有把“原始照片/视频 → 重建算法”的每一步都写在正文里，但从它的数据引擎、INSIGHT-Bench 预标注流程和官方 Real2Sim2Real 说明，可以把场景资产化过程还原成这样：

1. **采集与重建真实空间**  
   先用多视角图像、视频或 3D 扫描捕捉真实室内外空间。公开场景源里，HM3D / MP3D 属于 mesh-based 场景，Habitat-GS / InteriorGS 属于 3D Gaussian Splatting 场景，VLNVerse 也提供适合具身导航的仿真环境。需要强调的是，**这些场景源本身大多是公开数据集**；LightNav-0 论文没有展示一套完整的私有场景采集/重建数据集。它做的事情更偏向复用、统一和自动化标注，而不是从零扫描 2000 个场景。换句话说，LightNav-0 不是让模型直接看真实照片训练，而是先把已有/可得的空间资产变成可渲染的数字场景。

2. **选择可渲染的场景表示**  
   最终资产通常采用两种表示之一：
   - **Mesh**：适合传统 Habitat 仿真，几何边界明确，可以做碰撞和导航网格；
   - **3D Gaussian Splatting**：适合高保真、照片级渲染，尤其是室内外真实场景重建。
   
   LightNav-0 的 INSIGHT-Bench 同时使用了 mesh-based 和 Gaussian-splatting 场景，目的是让模型不依赖某一种渲染表示。

3. **建立导航网格和可采样视点**  
   只有 3D 外观还不够，必须知道哪里可通行。系统会在场景中构建 navigation mesh，并在可导航区域采样有效视点。这样仿真资产才具备“机器人能走、能渲染、能生成轨迹”的能力。

4. **统一到共同 3D target inventory**  
   不同来源的场景，无论原始格式是什么，都会先转换成同一种 3D 目标表示。论文的说法是：all scene sources are converted to a common 3D target inventory before episode synthesis。这一步是“可复用”的关键，因为后面的轨迹生成、目标标签和指令生成都不需要关心场景原本来自哪个数据集。

5. **自动做开放词汇语义预标注**  
   在采样视点上渲染 4 个 heading 的 RGB + metric depth，然后用 Molmo2 做 open-set pointing，把图像中的目标从 2D 提升到 3D。多个视角的检测结果再做一致性合并，只有空间 spread < 0.6 m 的目标实例才保留。这样场景里就有了稳定的 3D target 实例，供后续生成 object-point 标签。

6. **把静态数字孪生变成数据生成器**  
   有了导航网格、目标库存、渲染器和相机参数随机化，场景就不再只是“一个可看的模型”，而是可以反复采样任务、生成路线、渲染视频和动作标签的仿真资产。

所以，“可复用”的本质不是把真实场景存成一张全景图，而是把它变成 **可导航、可渲染、可标注、可随机化、可生成轨迹** 的数字资产。

#### 第三步：自动轨迹与语言指令生成

以论文提出的 INSIGHT-Bench 数据管线为例，一条训练 episode 大致是这样生成的：

1. **场景资产化**：HM3D、MP3D、Habitat-GS、InteriorGS、VLNVerse 等场景被统一成共同表示；
2. **目标预标注**：采样可导航视点，渲染 4 个 heading 的 RGB + metric depth；
3. **开放词汇定位**：用 Molmo2 做 open-set pointing，把图像中的目标提升到 3D；
4. **多视角一致性过滤**：同一个目标只有在至少两个不同视角下被观测到，且 3D 定位 spread < 0.6 m，才被保留；
5. **episode 合成**：选择目标与起始位姿，在 navigation mesh 上规划路线，锚定 stop，渲染第一视角视频和动作标签；
6. **指令生成**：既可以用 rule template 生成结构化指令，也可以用 video VLM 生成更自由的路线描述，再经过 LLM rewrite、语义检查和最终视觉到达验证。

这套管线让 mesh-based simulator 和 Gaussian-splatting 场景都能输出同一种轨迹格式，同时保证语言指令不是“看起来合理”，而是和实际渲染出的路线、目标位置对齐。

#### 第四步：Real，零样本部署并回流

训练完成后，同一个 checkpoint 被部署到未见过的真机和场景中。按照论文和官方说明，覆盖：

- 人形、四足、轮式、无人机等不同本体；
- 室内和室外场景；
- 静态目标和动态目标；
- 指令导航、物体导航和视觉跟踪。

所谓“Real2Sim2Real 飞轮”，是指真实部署中暴露出的新场景、新任务和新失败模式，会再被转成仿真资产和训练任务，进入下一轮数据生成与模型训练。

这套方案的价值在于：**真实数据定义分布边界，仿真数据在边界内规模化填充；部署又反过来提供新的分布边界。** 它并不是说真实机器人数据完全不重要，而是把真实数据的角色从“唯一训练来源”变成“分布定义器 + 最终验证器”。

### 3.4 缩放分析：场景多样性比参数和数据小时数更重要

论文里的 scaling analysis 很有信息量，三种资源的行为完全不同：

- **模型规模**：2B → 4B 明显提升，R2R SR/SPL 提升 8.6/7.4 点；但 8B 整体略差或表现混合，说明继续堆参数已经接近饱和。
- **数据量**：单调但边际递减。最后一半数据只换来 R2R SR 0.8 点提升。
- **环境覆盖**：从 1/8 的训练环境增加到全部环境，R2R SR/SPL 提升 16.7/16.2 点，RxR 提升 21.1/19.1 点。

结论很清楚：**对当前 4B 级别的导航模型来说，场景多样性是比参数量和“更多小时数”更可靠的杠杆。**

在统一单目前向接口下，LightNav-0 的成功率比 NaVid 高出一大截。这个 benchmark 对真实机器人部署更有参考意义。

### 4.5 远距离/长时程导航能力怎么样？

这个问题需要分两层看。

**第一层：长时程、长指令导航，是可以做的。**

LightNav-0 支持多步、长指令导航，论文也专门做了评测：

- RxR 是比 R2R 更长、更复杂的长时程 VLN，LightNav-0 达到 SR 73.6；
- INSIGHT-Bench 统一使用 300 步动作预算，覆盖室内外场景；
- 训练数据包含户外 3DGS 场景，因此户外导航相对基线有明显提升。

所以如果“远距离”指的是“跨房间、多路口、多步骤的长指令”，这是它重点验证过的能力。

**第二层：真正的长距离、大范围导航，证据不足，而且存在结构限制。**

LightNav-0 本质上是一个局部轨迹策略，不是一个带全局地图和全局路径规划器的导航系统：

- 每步只输出未来 10 个 SE(2) waypoint；
- 依靠压缩后的视觉历史维持上下文；
- 没有显式 metric map、拓扑地图、全局 localization 或 GPS 级目标管理；
- 决策是单一路径：当前帧 + 历史 + 指令 → pointing + 轨迹。

INSIGHT-Bench 的场景轴结果也能看出这一点：

| 场景类型 | LightNav-0 SR |
|---|---|
| Apartment | 61.1 |
| Outdoor | 34.2 |
| Institution | 29.2 |

户外和大规模机构场景明显更弱。也就是说，它能在户外做长指令，但还谈不上擅长长距离、稀疏地标、全局目标搜索。

论文结论里也明确写了：

> 当前模型使用单一决策路径，没有显式分离高频局部控制和较慢的语义规划；未来方向之一是加一个较慢的 VLM planner 做 long-horizon reasoning。

这说明作者自己也把“更强的长距离/长时程规划”视为后续扩展方向。

因此更准确的说法是：

```text
长时程室内外指令导航：能，且有 benchmark 支撑。
开放世界、公里级、依赖全局地图的长距离导航：目前证据不足，模型也缺少全局规划与长期记忆恢复机制。
```

LightNav-0 擅长把一段长任务切成连续、短视距的可执行轨迹，但“远距离导航”的全局可靠性和长程纠错能力仍然开放。

## 五、工程化：模型与机器人分离的部署架构

LightNav-0 的仓库不只是论文模型，还提供了一套比较完整的工程栈。

### 5.1 服务端 + 客户端

部署被拆成两个进程：

```text
GPU host                           robot
┌────────────────────────┐         ┌────────────────────────────┐
│ lightnav-serve         │◀─ JPEG ─│ camera → JPEG → base64     │
│ vLLM / HF backend      │─ 动作 ─▶│ instruction → WS client    │
│ 微批处理多个机器人会话   │         │ waypoint[0] → velocity     │
└────────────────────────┘         └────────────────────────────┘
```

- 模型跑在 GPU 主机上，通过 `lightnav-serve` 提供 WebSocket 服务；
- 机器人端只跑一个薄客户端：采集 JPEG 帧，发送指令，接收未来 waypoint，并执行第一个 waypoint；
- 机器人端不需要 GPU，也不需要 PyTorch，只需要 WebSocket 和 JPEG 编码。

多个机器人可以共享一个 server，每个连接是一个独立 session，并发请求被 micro-batch 到同一个推理引擎。按照文档，在单张现代 GPU 上，使用 `vllm_local` 后端时单步延迟约 **60–150 ms**，包括 ViT、LLM decode 和 waypoint decode。

### 5.2 输出协议：一个统一的轨迹接口

服务端返回的 `actions.actions` 是一个 `(H, 3)` 数组：

```text
[forward_m, lateral_m, yaw_rad]
```

- `forward_m`：前向位移；
- `lateral_m`：横向位移，正号向左；
- `yaw_rad`：偏航角，正号逆时针。

客户端通常只执行 `actions.actions[0]`，把它映射成机器人本地速度：

```python
v_forward = fwd / dt
w_yaw    = yaw / dt
```

也可以按 per-step 最大值归一化并 clip 到 `[-1, 1]`，再乘平台最大速度。

### 5.3 快速开始

```bash
git clone https://github.com/lightorigins/LightNav-0.git && cd LightNav-0
python3.11 -m venv .venv && source .venv/bin/activate
pip install -e ".[vllm,video]"
hf download LightOriginsHQ/LightNav-0 --local-dir checkpoints/LightNav-0

lightnav-predict --model_path checkpoints/LightNav-0 \
    --backend vllm_local --video clip.mp4 --fps 4 \
    --instruction "follow the person in the red shirt"
```

发布 checkpoint 自带 RVQ action decoder，因此推理时 `--model_path` 是唯一必须的资产参数。

### 5.4 真机栈

仓库中的 `robot_deploy/` 提供了一个完整 ROS 2 机载栈：

- camera driver；
- WebSocket client；
- MPC waypoint tracker；
- web control panel；
- Unitree Go2 和 LimX TRON 1 适配器；
- bring-your-own-robot adapter 接口。

`mujoco_demo/` 则是一个自包含的 MuJoCo TurtleBot + ProcTHOR 场景仿真，不需要 ROS、Habitat 或本地 GPU，可以在浏览器里直接对 `lightnav-serve` 发指令。

## 六、我看到的亮点

### 6.1 “不要预测头，要 token 接口”

LightNav-0 最有意思的地方，是它把导航能力收敛到了一个统一的生成式接口：

```text
指令 + 视频历史 → 双通道 pointing → RVQ 动作 token → 轨迹
```

pointing 是空间推理 trace，动作 token 是几何输出，中间没有任务分类器，也没有针对 VLN/ObjectNav/tracking 的独立 head。这让模型天然具备跨任务和跨本体的迁移基础。

### 6.2 记忆不是越长越细

历史压缩不是简单的“保留最近 N 帧”，而是用多分辨率、时间衰减的方式模拟遗忘曲线。它把“最近需要几何精度，远历史需要上下文”这个导航直觉落成了一个可配置的 token 预算机制。

### 6.3 缩放实验把结论说得很清楚

“参数饱和、数据边际递减、场景多样性最有效”的结论，对团队如何分配训练资源有直接指导意义。这也解释了为什么一个 4B 模型能做到 SOTA：把资源投到更广的场景覆盖，而不是继续堆 8B。

### 6.4 模型与机器人解耦

服务端/客户端分离的部署协议对机器人厂商很友好。机器人端不需要 GPU，只需要发 JPEG、收 waypoint，降低了在 Unitree Go2、LimX TRON 1 等平台上落地的门槛。

## 七、值得继续追问的地方

1. **真实世界证据还不够“量化”**  
   论文和仓库展示了人形、四足、轮式、无人机在未见过公园中的自主导航，但真实世界评测目前更像是 demo。INSIGHT-Bench 是更偏部署的模拟评测，但 episodes 和评估代码说明要“另行发布”。如果后续能给出跨本体、跨场景的真机统计指标，说服力会更强。

2. **单目前向 120° 是否是最终形态**  
   在 INSIGHT-Bench 中统一使用 120° 前向 RGB，是为了衡量公平的单目能力。但真实机器人面对窄门、后方障碍、动态遮挡时，单目前向可能不够。模型本身支持更宽 FOV 和多种 camera 配置，但实际能力需要更多验证。

3. **开源侧更偏推理/部署**  
   从 README 看，开源内容包括模型 checkpoint、推理与评测 harness、部署栈。Real2Sim2Real 的数据合成管线、训练代码和 INSIGHT-Bench episodes 似乎没有全部随仓库发布。如果要完全复现训练，可能还需要等后续 release 或看论文细节。

4. **EVT-Bench 的 License 问题**  
   代码是 Apache 2.0，但 EVT-Bench 本身是 CC BY-NC-SA 4.0，仓库没有重新分发。做商业集成时需要注意数据/benchmark 的许可边界。

## 八、总结

LightNav-0 给出的路线不是“更强的导航专用网络”，而是：

> 先用一个足够好的 VLM 作为空间智能来源，再用统一 token 接口把它对齐到动作空间。

在这个框架下，指令导航、开放词汇物体导航和视觉跟踪不再是三个模型，而是同一个模型在不同语言指令下的三种行为。它的 4B 规模、单目 RGB 输入、共享 checkpoint、跨本体部署协议，都让它在通用导航基础模型这个方向上很有代表性。

对做具身导航的团队来说，LightNav-0 至少有这几个可以借鉴的点：

- 把空间意图显式表达为 pointing token，而不是直接端到端回归轨迹；
- 用 RVQ 残差量化表达动作，使 token 前缀也能解码成可执行轨迹；
- 用时间衰减的多分辨率历史压缩，而不是无限增长的视频 token；
- 把训练资源投到场景多样性，而不是盲目扩大模型或数据小时数；
- 通过“GPU server + 薄机器人 client”实现跨本体部署。

它当然还不是终点。真实世界中的长程任务、异常恢复、动态密集环境和商业化可靠性，仍然需要更多数据和更多公开评测。但至少在“让 VLM 的空间智能直接变成通用导航”这件事上，LightNav-0 给出了一个清晰、可复现、可部署的开源样本。
