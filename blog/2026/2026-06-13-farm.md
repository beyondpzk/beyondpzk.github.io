# FARM：用关系空间记忆找到任何东西——物体级认知地图的在线构建与语言检索

> **论文**：*FARM: Find Anything using Relational Spatial Memory*  
> **作者**：Siming He、Leo Huang、Adam Lilja、Fabio Hübel、Jonas Frey、Marco Pavone、S. Shankar Sastry、Jitendra Malik、Claire Tomlin（UC Berkeley + Stanford）  
> **发布时间**：2026-06-13（arXiv v1，目前为预印本）  
> **arXiv**：https://arxiv.org/abs/2606.15476  
> **代码**：https://github.com/GoldenGait/FARM-Project （AGPL-3.0）  
> **主页/数据**：https://goldengait.github.io/farm/ ｜ https://huggingface.co/datasets/GoldenGait/FARM-Scenes

## 一句话总结

FARM 为机器人构建一个**以物体为中心的关系空间记忆**（relational spatial memory）：每个物体被表示为一个 3D 高斯 + 多模态检索嵌入 + 代表性视角，物体间只存"共视/邻近"两类低阶关系；查询时把"飞镖盘下方、海报左边那盏高台灯"这类自由形式关系语言编译成带 16 个空间谓词的一阶逻辑查询图，经软评分 + VLM 重排序定位目标实例。全系统**零训练**（纯基础模型组合），在 67 个场景、44,031 条查询上大幅超越 BBQ/DAAAM/RynnBrain，并已在 Spot + Jetson Thor 上真机部署。

## 动机：为什么"找东西"需要专门的空间记忆

在仓库、工地、家庭这类物体密集环境中，用户指称目标的方式往往不是类别名，而是**与其他物体的空间关系**——"带 TOI TOI 标识、最靠近白色 DBE 货车的蓝色移动厕所"。现有方案对此有三类不足：

1. **闭词汇语义 SLAM / 3D 场景图**：不支持开放词汇；
2. **开放词汇场景图**（BBQ、DAAAM 等）：需跨场景调参、依赖离线后处理；CLIP 类嵌入抓不住多概念关系；端到端 VLM 在图上推理脆弱（FARM 消融发现甚至不如纯嵌入检索）；
3. **VLM 直接看历史帧/长视频**：受上下文窗口限制，无法覆盖大场景的数千个视角。

FARM 的出发点借自 Tolman 的认知地图（cognitive map）研究：动物构建持久、结构化的空间记忆以支持灵活推理——机器人也应该有一张**以物体为节点的认知地图**，在线构建、按需检索。

## 核心方法

### 1. 记忆表示：每物体一个 3D 高斯

记忆中的每个实体 $\mathcal{E}^i = \langle \mathcal{A}^i, \mathcal{R}^i \rangle$，属性含五项：

- 一个 **3D 高斯** $\mathcal{N}(\mu^i, \Sigma^i)$ 概括位置与空间范围；
- 检测时的 DINOv3 外观特征（跨视角关联用）；
- 至多 k 个代表性视角（带位姿 RGB crop）；
- VLM 开放词汇 caption；
- **三个检索嵌入**：caption 文本嵌入（Qwen3-Embedding-0.6B）、SigLIP2 图像嵌入、Qwen3-VL 图像嵌入。

关系 $\mathcal{R}$ **刻意只存两类可快速推导的低阶关系**：共视边 + 邻近边（高斯间 Hellinger 距离）。高阶关系（left-of、containment 等）不存——会指数增长，留给检索时按需恢复。

**为什么每物体只用一个高斯**（论文第 19 页专门用一节 *"Why a single Gaussian per entity?"* 解释，这是工程精髓）：

**三种几何表示的对比：**

| 表示方式 | 需要超参数 | 更新复杂度 | 尺度敏感性 |
|----------|-----------|-----------|-----------|
| 点云 | 点密度/距离阈值 | O(n) | 高 |
| 体素网格 | 体素边长 | O(n³) | 高 |
| 3D 高斯 | ❌ 无需 | O(1) | 低 |

**理由一：resolution-free（无分辨率超参数）。** 点云/体素需要全局密度或体素边长超参：体素边长设太小，室外场景内存爆炸；设太大，室内小物体被"溶解"。而高斯分布 $\mathcal{N}(\mu,\Sigma)$ 本身没有分辨率概念，协方差 $\Sigma$ 自适应地编码对象的空间范围，同一套参数就能处理 ScanNet 房间、HM3D 公寓和室外工地。论文原话："A Gaussian carries no such hyperparameter"。

**理由二：O(1) 在线闭式更新。** 用充分统计量合并新观测：$M_1 = w\mu$，$M_2 = w(\Sigma + \mu\mu^\top)$；新观测到来时直接累加统计量，再恢复 $\mu$ 和 $\Sigma$。这样每个对象的存储 footprint 恒定、每次更新的代价恒定，适合在线系统，不会随着观测次数增加而变慢。

**理由三：尺度不变的匹配度量。** Hellinger 距离用来判断两个高斯是否匹配，$d_H(\mathcal{N}_1,\mathcal{N}_2)\in[0,1]$：无量纲、有界，因此**同一个匹配阈值可以跨 10¹~10⁴ m² 场景复用**。对比欧氏距离判断位置接近程度，室内阈值可能设 0.1 m、室外可能要 5 m，得按场景重新调参。

**实际效果（论文 Figure 7）：** Figure 7a 映射延迟随轨迹长度保持稳定，不随场景变大而增长；Figure 7b 定位精度随场景面积平缓下降而非灾难性崩溃，从 15 m² 到 15,000 m² 都能工作。

**与 3DGS（3D Gaussian Splatting）的区别：** FARM 是"每对象一个高斯"的**对象级几何抽象**，3DGS（Kerbl et al. 2023）是数十万个小高斯的密集点云，用于照片级实时渲染；FARM 的协方差编码对象范围并关联到语义，3DGS 的协方差编码局部表面、纯几何外观。

**一句话总结：** 无需调分辨率超参（室内外一套参数通吃） + O(1) 在线更新（实时 ~8 Hz 不随观测变慢） + Hellinger 距离有界（单一阈值跨 10³ 尺度），这正是 FARM 能同时处理 1,600 m² 多层住宅和 15,000 m² 建筑工地的**核心表示论基础**。

### 2. 在线建图：每帧 7 步同步循环

分割（YOLOE 开放词汇检测 + mask 反投影为 3D 高斯）→ 过滤级联（丢弃贴图边框/前景过少/墙地板等无信息类别）→ 近邻搜索（特征预筛 + Hellinger 距离精筛）→ **union-find 对应**（解决"多检测认领同一实体"与"一检测桥接两实体"）→ 高斯融合 → 高质量视角选择 → 共视更新（bitset 邻接 + 时间衰减）。

**异步 VLM 富化**：视角集变化的实体入队，后台 worker 生成结构化 caption 并算三种检索嵌入写回——不阻塞建图主循环。建图吞吐约 **8 Hz**，全部向量化 CUDA。

### 2.1 在线建图全貌（Figure 3）

Figure 3 把在线记忆构建拆成三部分：

| 部分 | 内容 | 速率 |
|------|------|------|
| (a) 实时记忆构建主循环 | 同步关键路径 | 5–10 Hz（约 8 Hz） |
| (b) 视觉–语言对象编码 | 异步后台 | ~2 Hz |
| (c) 最终记忆表示 | 存储结构 | — |

**(a) 同步主循环**：RGB + 深度 + 相机位姿 → YOLOE 开放词汇检测 → 3D 提升（mask 反投影 + 高斯拟合为 $\mathcal{N}(\mu,\Sigma)$）→ 几何过滤（Hellinger 距离）→ 语义过滤（外观余弦相似度）→ 关联决策（Match 则更新对象，否则新建对象）。这一步在关键路径上，每帧都执行。

**(b) 异步对象编码**：当对象的高质量视图集合变化时入队；后台 vLLM 工作线程用 Qwen3.5-9B 生成结构化 JSON caption，并同时算三种检索嵌入（Qwen3-Embedding-0.6B 文本、SigLIP2 图像、Qwen3-VL 图像）。论文原话强调其必要性："Because the mapping loop is never blocked, the steady-state frame rate is set by the synchronous loop alone, not by VLM throughput"（第 19 页）——主循环帧率只由同步部分决定，不受 VLM 吞吐限制。

**(c) 最终记忆表示**：每个实体 $\mathcal{E}_t^i=\langle\mathcal{A}_t^i,\mathcal{R}_t^i\rangle$，属性含 3D 高斯、外观特征、最多 k 个代表视图、JSON caption、三种检索嵌入；关系只存共视边 + 邻接边，不存高阶关系（containment / left-of / between 等），留到查询时动态计算。

**图内示例（ScanNet 0000）**：已有 white round shallow bowl、black slotted plastic spatula、metallic cylindrical pot with handle、white refrigerator with ice dispenser、white plastic trash can with lid、white plastic trash can with handles 等对象；当第 7 个检测（white round shiny bowl）进来时，先做几何过滤（Hellinger 距离）和语义过滤（余弦相似度），匹配到对象 1 就更新 $\mu',\Sigma'$ 与嵌入 $z_1$，否则新建 $z_7$。

**设计哲学**：同步/异步分离保证实时帧率（VLM 不阻塞主循环）、单高斯 per 对象（无超参 / O(1) 更新 / 尺度不变）、三嵌入融合（文本 + 视觉语义 + 视觉细节）、关系查询时计算（避免指数级存储）。

### 3. 关系检索：compile → score → verify 三阶段

**不让 VLM 端到端看图回答**。Qwen3.5-9B 先把查询编译为类型化查询图——目标变量 + 锚点变量 + 谓词集，等价于锚点存在量化的一阶逻辑式：

$$\varphi_q(x_\star) = \exists\, a_1,\dots,a_m \Big( \bigwedge s_\sigma(v) \wedge \bigwedge \rho(\mathbf{v},\alpha) \Big)$$

谓词库为 **16 个固定谓词名**（参数开放词汇）：`Near, On, Above, Below, NextTo, Between, Inside, InRegion, LeftOf, RightOf, InFrontOf, Behind, Closest, Farthest, HasAttribute, IsCategory`；集合外的空间关系由 LLM 分解为这些谓词的组合。

**软评分**的两个关键设计：

- **星形分解**：典型指代表达是星形图，$\max_{x_\star,a_1,\dots,a_m}\sum_i \rho_i(x_\star,a_i) = \max_{x_\star}\sum_i \max_{a_i}\rho_i(x_\star,a_i)$——精确绑定从指数级降到 $O(|\Phi_q| K_t K_a)$；
- **软合取**：谓词分取几何平均后与语义分混合 $s = s_{\mathrm{sem}}[(1-w) + w\bar{g}]$——锚点错了最多把语义分减半，不会删除候选；硬过滤会让召回随锚点数乘性退化。

候选检索对全池做 **reciprocal-rank fusion**（四个查询通道跨三种嵌入空间，不截断 top-k）；最后 top-5 由 VLM 重排序（渲染候选为中心的示意图打分）。**FARM∘ = 无重排序版本**，重排序是"难场景才开的部署旋钮"。

全系统无训练，纯组合现有基础模型：YOLOE（检测）、DINOv3（合并特征）、Qwen3.5-9B（caption + 查询解析 + 重排序）、Qwen3-Embedding-0.6B、SigLIP2、Qwen3-VL-Embedding-2B。

## 关键结果

**主结果**（visible-mask IoU@0.1，67 场景、44,031 条查询，A@1 / R@10，%）：

| 方法 | ScanNet–30 | HM3D–30 | FARM-Scenes |
|---|---|---|---|
| BBQ | 15.4 / 23.5 | 5.3 / 12.8 | 7.4 / 9.6 |
| DAAAM+RynnBrain | 29.3 / — | 6.1 / — | 15.1 / — |
| FARM∘ | 33.0 / 74.6 | 6.7 / 26.9 | 16.3 / 47.3 |
| **FARM** | **35.9 / 74.6** | **7.9 / 26.9** | **24.2 / 47.3** |

相对 BBQ 提升 142%/164%/224%（A@1/R@5/R@10）。注意 HM3D 上绝对数字很低（A@1 仅 7.9%）——该基准本身极难，论文如实呈现。

**效率**：建图 ~8Hz（59~130 ms/帧）；记忆体积 ScanNet ~23 MiB、HM3D ~125 MiB、大场景 ~65 MiB；查询延迟 1.7~4.1 s（对比 DAAAM+G 的 66 s）。

**消融亮点**：

- **差距主要来自建图器而非检索器**：同样的嵌入与检索，BBQ→FARM 建图器使 A@1 从 5.4 → 23.0（4.3 倍）；
- 纯视觉嵌入（SigLIP2）崩溃（HM3D A@1 0.3），caption 文本嵌入是主力，三嵌入融合最佳；
- **重排序不对称**：简单场景反而有害（ScanNet 41.6→40.6），难场景显著提升（FARM-Scenes 10.8→15.5）。

**真机**：Spot + Odin 1 感知单元（RGB-D + 内置 LiDAR-VIO，免外部 SLAM）+ Jetson Thor。Stage 1 遥操作探索建图 → Stage 2 关系查询 → grounding → 沿 Stage-1 轨迹构图 + Dijkstra 取路径。8 条演示查询 6 成功 2 失败——两条失败案例（"桌下的纸箱""白色桌子和机器人之间的椅子"）在**补充属性修饰后成功**，很能说明系统的边界在哪。

## 代码与复现

仓库结构清晰，核心库 `scene_graph` 零 ROS 依赖（ROS 2 层独立在 `ros/`），在线/离线复用同一算法代码：

- `map_update/`（高斯融合、union-find、共视）、`retrieval/spatial_reasoning/`（查询解析 + 谓词执行）、`eval/`（ReferIt3D/IRef-VLA/FARM-Scenes 全套评测 harness）、`visualization/`（viser 3D 查看器 + 查询面板）；
- **只支持 Docker**（CUDA 12.8 + ROS 2 Humble），vLLM 起三个服务（Qwen3.5-9B / Qwen3-Embedding / Qwen3-VL-Embedding）；
- **资源门槛不低**：全栈约 50 GB 显存（最大场景 ~65 GB），真机靠 Jetson Thor 的 128 GB 统一内存装下；
- **FARM-Scenes 数据集公开**（含预建 scene graph，可零重建直接体验检索）；论文级 DINOv3 ViT-S+/16 是 HF gated 模型，回退版会导致房间级场景物体碎裂 ~2×；
- License 是 **AGPL-3.0**（YOLOE 传染），商用需注意。

## 局限

- 谓词函数手工指定、未校准（`Near` 随距离衰减过快会误伤正确目标）；语义与空间分用均匀权重；
- 只支持"目标↔锚点"关系，**锚点间的组合推理不支持**（不能先用一个关系消歧锚点再定位目标）；
- 大场景上"候选在 top-10 但 top-1 选错"仍是主要失败模式；
- HM3D 级难度下绝对精度仍低；acc@1 受 LLM 采样波动 ±1~3 点。

### 环境变化的局限：online memory，不是 lifelong memory

FARM 本质上是 **"online memory construction"（在线记忆构建）**，而不是 **"lifelong memory management"（终身记忆管理）**——它假设环境在查询阶段基本是静态的，长期部署下的变化处理是一个明显缺口。

**能处理 vs 不能处理的变化：**

| 变化类型 | 例子 | 能否处理 |
|----------|------|----------|
| 视角变化 | 从不同角度看同一物体 | ✅ 高斯融合就是为此设计 |
| 临时遮挡 | 物体被暂时挡住 | ✅ 记忆是持久化的 |
| 物体新增 | 新家具搬进房间 | ✅ 会创建新对象 |
| 物体位移 | 椅子被推到房间另一侧 | ⚠️ 会新建对象，旧对象残留 |
| 物体移除 | 桌上的杯子被拿走 | ❌ 旧对象残留在记忆中 |
| 场景重构 | 房间重新布置 | ❌ 需要重建记忆 |

**对象生命周期管理不完整。** 论文第 19 页提到有 "periodic pruning pass"（定期剪枝），但没细说策略：多久没观测就删除？怎么区分"物体被移走"和"机器人还没走到那个区域"？这会带来两类具体问题：

- **旧对象残留**：桌上的杯子被拿走，对象仍标记为 active；查询"桌子上的杯子"仍会返回这个已不存在的杯子；
- **移动后的身份混淆**：椅子从位置 A 移到 B，在 B 处几何/语义匹配失败，于是新建对象，系统错误地认为存在"两把椅子"（旧的在 A、新的在 B）。

**可能的解决方向（论文未实现）：**

| 方向 | 思路 | 挑战 |
|------|------|------|
| 时间衰减 | 长时间未观测的对象置信度下降 | 区分"未观测"与"在另一个房间" |
| 重定位机制 | 定期回访已建图区域验证对象 | 增加探索开销 |
| 变化检测 | 比较当前观测与记忆的显著差异 | 需要语义理解"什么变化重要" |
| 用户反馈 | 查询失败时触发局部重建 | 依赖交互 |
| 多假设跟踪 | 同一对象维持多个位置假设 | 内存与计算开销 |

这一点不是 FARM 独有的局限，而是场景图 / 时空记忆领域的开放问题：Clio 靠任务条件化压缩但同样假设静态，DAAAM 用 4D 场景图引入时间维度但计算开销大，Khronos 做时空 SLAM 但侧重度量而非语义变化。论文的 Stage 1（完整遍历建图）→ Stage 2（已建图上查询导航）也是"建图-查询分离"模式，查询阶段默认环境静态；对家庭/仓库这类需要运行数周、数月的场景，长期变化管理仍需额外机制。

## 与 Teach-and-Repeat 路线的关系

FARM 与我们讨论的室内 teach-and-repeat 方案（见 [室内轻地图导航：Teach-and-Repeat 与语义记忆](/blog/2026/2026-09-29-indoor-teach-repeat-navigation)）形成有趣的对照与互补：

- **同为"先转一圈再服务"**：FARM 的 Stage 1 遥操作建图就是 teach，Stage 2 检索+导航就是 repeat——但它建的是**物体级语义记忆**（回答"X 在哪"），GuideNav 建的是**路线级视觉记忆**（回答"怎么走"）；
- **可以拼起来**：FARM 把"去厨房"解析成物体实例和 3D 位置，GuideNav/NoMaD 负责走到那——FARM 场景图里的"代表性视角"甚至可以天然充当关键帧图的语义标签层；
- **代价差异明显**：FARM 需要 RGB-D + 位姿 + 50GB 显存级算力，GuideNav 纯 RGB + Jetson Orin 就够。轻量巡检走 GuideNav，需要"找任何东西"的语义能力再上 FARM。
