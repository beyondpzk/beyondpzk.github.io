# NavHarness 用目标验证管理长程导航与记忆

机器人收到“经过绿沙发，从门口出去，再右转到黄色椅子旁”的指令，可以连续生成看起来合理的动作，却未必真的完成了每个阶段。一次提前转弯就会让后续判断建立在错误进度上。NavHarness 给每个局部目标配上可观察的完成条件，让任务推进以新观测为依据。

完成验证还有第二个用途：标记哪些历史可以压缩。已完成阶段的交互记录被整理为路线摘要、验证结果和关键帧，当前目标及未完成事项继续保留。论文的核心是目标、验证和记忆共享同一个进度边界。

> 论文：*NavHarness: Adaptive Goals for Vision-and-Language Navigation*  
> 作者：Haoxiang Shi、Zaijing Li、Muhe Ding 等  
> 版本：arXiv:2609.39915v1，2026 年 9 月 30 日  
> [论文](https://arxiv.org/abs/2609.39915v1) · [全文](https://arxiv.org/html/2609.39915v1) · [项目入口](https://Navharness.github.io)

## 长程任务需要显式区分执行与完成

动作命令表示系统打算做什么；执行后的图像才提供实际发生了什么的证据。机器人发出了右转命令，并不意味着它已经看到正确的门口；远处看见目标，也不意味着它已经到达目标旁边。

如果这些区别没有进入状态管理，局部错误会改变模型对整条路线的解释。另一方面，保留全部图像和工具记录会增加每次决策输入；简单截断又可能删除绕路原因或未完成指令。

NavHarness 用同一机制处理两者：先判断局部目标是否完成，再决定推进目标和压缩历史。遇到偏航时可以生成纠正目标，但仍保留原指令和未解决阶段。

## 四个角色如何协作

论文中的 Agent 是分工角色，不意味着必须部署四个独立训练的模型。

| 角色 | 输入重点 | 产出与职责 |
|---|---|---|
| Goal Agent | 原指令、当前观测、历史 | 当前局部目标及验证问题 |
| Visuomotor Agent | 局部目标、观测、验证反馈 | 前进、转向、停止或短动作序列 |
| Verify Agent | 执行后观测、目标及验证问题 | 完成判断、支持证据与未满足条件 |
| Memory Agent | 已验证阶段及原有记忆 | 摘要、验证结果和关键帧 |

典型循环是生成目标和验证问题，执行短动作序列，检查新观测。如果仍未完成就继续执行；如果场景与目标不符就调整局部目标；确认完成后压缩该阶段，再制定下一个目标。

例如，把“穿过门口后右转”转成一个局部目标时，验证问题应该检查是否已经通过门口，以及转向后是否看到指令相关区域。只问“是否看到门”会让远处可见的门被误当成到达证据。这个例子说明可观察条件的设计作用，并非论文固定提示词。

## 验证反馈需要进入下一轮动作

Verify Agent 在每次交互之后读取最新图像和执行记录。它的输入不包括自己即将生成的判断，避免把尚未形成的结论混进证据。

反馈既可以确认完成，也可以报告条件未满足或证据不确定。论文举例：如果验证问题要求转向后同时看见绿沙发与门口，只看见沙发就不满足条件。

这样的反馈会进入执行角色的下一轮输入，也会影响目标角色是否生成纠正目标。最终停止条件同样需要验证。这里的“完成”是模型根据可见证据形成的判断，可靠性仍受视野、遮挡和空间推理能力约束。

## 记忆压缩保留什么

论文将共享上下文分为压缩记忆与近期交互记录。确认目标完成后，Memory Agent 把上一压缩边界以来的历史合并成三类内容：已执行目标及路线关系摘要、对应验证结果、验证位置的视觉关键帧。

关键帧使后续判断仍能访问部分原始视觉证据。当前目标、近期观测和未完成状态继续保留。目标被修订时，也不能把尚未完成的原阶段标记为完成。

这种设计可以理解为按任务阶段组织记忆。阶段划分也会带来风险：如果验证错误地宣布完成，后续压缩可能放大错误，把一个未经充分确认的阶段写成既成事实。因此，验证质量和记忆质量存在直接耦合。

## 仿真比较必须看清子集与骨干

作者分别评测 100 条 R2R-CE 和 100 条 RxR-CE；R2R 使用 Open-Nav 子集。NavHarness 与论文中的 Codex CLI 基线共享骨干、episode 和观测动作接口，只使用指令及前向 RGB，没有参考轨迹或评测器反馈。

下表保留作者的模型名称与报告值。这些名称表示论文实验配置，不代表这里对模型可获得性的说明。SR/SPL 单位为百分比。

| 骨干与配置 | R2R SR | R2R SPL | RxR SR | RxR SPL |
|---|---:|---:|---:|---:|
| GPT-5.6-Sol，基线 | 62.6 | 44.5 | 28.0 | 21.0 |
| GPT-5.6-Sol，NavHarness 无压缩 | 67.0 | 47.9 | 34.0 | 25.0 |
| GPT-6-Astra，基线 | 74.0 | 62.5 | 76.3 | 60.0 |
| GPT-6-Astra，NavHarness 无压缩 | 79.0 | 66.6 | 82.5 | 64.7 |

这些配对结果支持目标与验证框架在同一骨干上的作用。但主表汇集的其他论文结果保留各自原始协议，不能把这里的百条子集成绩与完整 validation-unseen 成绩直接排序。

这里的 zero-shot 表示没有为该导航任务进行专门训练；它仍依赖预训练多模态模型能力。79.0% 与 82.5% 的主成绩属于无记忆压缩配置，不能说是四个角色开启压缩后的成绩。

## 压缩收益包含明显的性能取舍

论文 Table 2 的总 token 统计包含各角色调用和压缩开销。局部输入变短，不一定带来相同幅度的整个任务 token 节省。

| 骨干与数据集 | 无压缩 SR | 压缩后 SR | 总 token 节省 |
|---|---:|---:|---:|
| GPT-5.6-Sol，R2R | 67.0 | 66.0 | 35.94% |
| GPT-5.6-Sol，RxR | 34.0 | 32.0 | 56.59% |
| GPT-6-Astra，R2R | 79.0 | 77.0 | 5.52% |
| GPT-6-Astra，RxR | 82.5 | 81.0 | 4.05% |

强骨干的累计节省较小。GPT-6-Astra 在 RxR 的 SPL 从 64.7% 降至 58.3%，说明路径效率也可能受压缩影响。弱骨干节省更多 token，但仍有 SR 损失。

作者展示的局部上下文下降 27.7%—48.1% 属于特定决策时刻；它与整个任务总 token 节省是不同统计量。效率均值还排除了使用记录不完整的任务，阅读结果时应保留这一口径。

框架消融在三种骨干上观察到收益，但没有分别隔离 Goal Agent 与 Verify Agent 的独立贡献。因此，可以支持整体组织方式有效，尚不能精确分配每个角色的增益。

## 真机结果说明什么

真机采用 Unitree Go2 与前装 RealSense D435i，仅使用 RGB。8 条约 15—20m 的路线覆盖走廊、教室、实验室、楼梯与户外，每条重复三次，共 24 次。作者报告 SR 为 83.3%，平均 NE 为 1.51m。

这些实验展示了有序地标决策和场景转换的可行性，但只有八条独立路线，重复试验不会增加环境多样性。对照方法使用论文提供的聚合结果，正文主表不足以证明所有对照都经历了完全相同的重跑与部署条件。

作者明确指出远端闭源模型带来较大的推理成本和通信延迟，单 RGB 相机还可能漏掉视野外障碍。该系统更适合研究高层任务组织，其高频避障与运动控制能力需要结合底层系统评估。

## 适合迁移到工程系统的设计

值得借鉴的是把目标、完成证据和未完成状态作为结构化接口。工程实现可以为每个目标记录前置条件、预计可见证据、失败原因以及确认所用图像时间戳，再以这些记录控制任务推进。

若部署预算有限，可以让本地策略持续执行，将高成本推理集中在目标生成、异常恢复和完成验证。这是基于论文的系统建议，调用触发时机及节省幅度需要重新验证。

与 [LiveVLN](/blog/2026/2026-10-08-livevln) 结合时，还要明确“动作已提交”“动作已执行”和“目标已完成”三个状态。缓冲中的动作不能作为完成证据；验证应对应实际执行后的观测。
