# RACI 责任分工：谁执行、谁负责、征询谁、告知谁

> 文中的人物、项目、时间和指标均为教学示例，不对应真实个人或组织。

**—— 把“大家配合一下”，变成能执行、能验收、能交接的分工**

> 适用对象：团队负责人、项目负责人，以及经常需要跨部门推进事情的人。
> 解决的痛点：多人参与却无人收口；执行人没有决策权；所有人都要过一遍，事情迟迟推进不了。
> 阅读方式：先理解四种角色，再照着案例填一张自己的责任表。

## 第一章 什么是 RACI：给每项工作明确四种关系

RACI 是一种**责任分配矩阵**。行写任务、交付物或决策，列写参与角色，交叉处用四个字母标明各自的责任。它帮助团队在开工前回答四个问题：

| 字母 | 英文 | 中文含义 | 要回答的问题 | 实际动作 |
| --- | --- | --- | --- | --- |
| **R** | Responsible | 执行人 | 谁把工作做出来？ | 实施、交付、报告进度与阻塞 |
| **A** | Accountable | 最终负责人 | 谁对这项结果负责，并在授权范围内作最终决定？ | 明确目标、协调资源、组织验收、处理升级 |
| **C** | Consulted | 被征询人 | 做决定或完成工作前，需要听谁的专业意见？ | 提供约束、建议与风险判断，双向沟通 |
| **I** | Informed | 被告知人 | 哪些人需要知道进展或结果？ | 按约定接收信息，通常不参与该项审批 |

基本规则是：**每项工作恰好一个 A，至少一个 R；同一个人可以兼任 A/R。** R 可以有多个，但应继续说明各自的交付边界；C、I 按需设置，不必每行凑齐四类人。定义与单一 A 原则可参考 [PMI 对 RACI 的说明](https://www.pmi.org/blog/stakeholder-management-raci)。

### 1. 最容易混淆的 R 与 A

以“交付一份客户方案”为例：

- 工程师是 **R**：调研需求、编写方案、补齐数据、修改问题。
- 方案负责人是 **A**：确认方案目标和资源，处理分歧，对最终交付负责。
- 技术专家是 **C**：在定稿前评审关键技术假设。
- 销售负责人是 **I**：接收定稿与进度信息，以便安排后续沟通。

R 不能只说“我把文件发了”；还要按约定完成交付、响应问题。A 也不能只说“我已经安排人做了”；还要确保目标有人实现、阻塞有人处理、结果有人接收。

**角色随任务变化。** 技术负责人可能是技术方案的 A，却只是商务报价的 C。A 不必永远是职位最高的人，但必须拥有相应授权和资源协调渠道。

### 2. C 与 I 的差别在沟通方式

**C 要在决策前被征询，I 按约定接收进展或结果。** 把评审专家放成 I，容易出现“都做完了才告诉我”；把所有知情人都放成 C，容易出现“每个人都要发表意见才能继续”。

C 的建议需要被认真处理，但 **C 身份本身不自动赋予否决权**。涉及公司明确规定的安全、财务或其他强制审批时，应保留审批流程，必要时单独列一行审批任务，明确其 A 和 R。

### 3. RACI 适合什么场景

它特别适合跨部门项目、重复执行的流程、多人交接，以及经常发生职责争议的工作。一个人独立完成的简单任务，直接写清执行人、期限和验收标准通常就够了。

RACI 主要回答“谁承担什么责任”。**排期、投入多少资源、做到什么标准、出了问题怎么升级，仍要另外写清楚。**

## 第二章 怎么建表：先定义结果，再分配角色

**场景说明**：准备启动一个跨部门项目，大家都愿意参与，但谁做什么、谁能决定什么还不清楚。

**❌ 错误示范**：

> “产品负责需求，研发负责技术，测试负责质量，项目经理负责推进。大家多沟通。”

这种说法只有部门职责，没有明确交付物。“负责质量”究竟包括测试执行、报告签发，还是上线放行，仍然可能各有理解。

**✅ 高气场话术**：

> “我们按交付物把事情拆开。每一项先确定验收结果，再明确执行人和最终负责人。
> 今天把需求基线、部署包、测试报告、上线决定四项定下来，每项都补上时间、验收条件和升级路径。涉及谁的授权，请当事人确认。”

**执行要点：按下面六步完成第一版。**

1. **列结果**：把“推进上线”拆成“确认需求基线”“交付部署包”“出具测试报告”“作出上线决定”。一行要能判断是否完成。
2. **定 A**：找真正能对该项结果负责的人。若两方都要求最终决定权，先拆分决策边界，仍无法解决时请共同上级或项目发起人裁定。
3. **定 R**：落实实际交付人。多个 R 需要明确子任务与交接；用部门角色建表后，还要映射到具体姓名。
4. **定 C、I**：只纳入必要参与者，约定征询时点和通知渠道。
5. **补执行条件**：为任务补充截止时间、验收标准、依赖、资源与升级对象。
6. **共同确认并维护**：让相关人员确认职责和授权；人员、范围、期限变化时更新版本并通知受影响者。

**建完后横着查任务，竖着查人员。** 横向看有没有缺 A、缺 R 或多个 A；纵向看某个人是否承担了过多任务，成为排队瓶颈。

## 第三章 实际用例一：把 AI 模型部署到机器人

**场景说明**：算法团队完成一个模型，准备部署到机器人上的 Orin NX。产品、算法、部署、测试共同参与。以下为教学示例，职责需按实际组织授权调整。

**❌ 错误示范**：

> “算法把模型给部署，部署跑通后测试看一下，没问题就上线。”

问题在于：离线效果好是否等于板端可用；量化后的精度变化谁评估；测试通过后谁决定上线；上线当天由谁执行。这些都没说清。

### 1. 把交付与决策拆开

表中每列代表一名已指定的负责人或执行代表。`A/R` 表示同一人同时负责结果和执行；`—` 表示该项未分配角色。

| 任务 / 交付物 | 产品负责人 | 算法负责人 | 部署工程师 | 测试负责人 | 发布负责人 |
| --- | --- | --- | --- | --- | --- |
| 确认场景与验收指标基线 | A/R | C | C | C | I |
| 交付模型、版本及离线评测报告 | I | A/R | C | C | I |
| 交付板端部署包及运行说明 | I | C | A/R | C | I |
| 出具板端性能与精度测试报告 | I | C | C | A/R | I |
| 根据验收证据作出上线决定 | C | C | C | R | A |
| 执行发布并提交验证记录 | I | C | R | C | A |

这里假定发布负责人已获得上线决策授权。测试负责人在“上线决定”一行担任 R，是负责准备验收证据和放行建议；最终决定由 A 作出。实际组织若由产品负责人决定业务上线，应相应调整 A。

部署工程师担任部署包的 A/R，只表示对这个交付物负责，并不自动拥有业务上线决定权。

### 2. 给分工配上可验收的条件

| 交付物 | 建议写进任务卡的验收条件 | 交接对象 |
| --- | --- | --- |
| 验收指标基线 | 明确业务成功条件、时延与精度口径、测试场景、失败判定；阈值在开工前确认 | 算法、部署、测试 |
| 模型与离线报告 | 模型版本、输入输出说明、依赖、评测数据版本及已知限制齐全 | 部署工程师 |
| 板端部署包 | 版本可追溯；注明运行环境、功耗模式、频率设置；提供复现与回退步骤 | 测试负责人 |
| 板端测试报告 | 对照约定指标给出结果，记录设备条件、持续运行表现及未关闭问题 | 发布负责人 |
| 发布验证记录 | 记录部署版本、验证结果、异常情况和是否触发回退 | 发布负责人及相关知情人 |

“能运行”通常不足以表示验收通过。技术指标应来自项目目标，不能临时挑选一项最有利的测试结果作为上线依据。

**✅ 高气场话术**：

> “这次上线分成模型交付、板端部署、测试结论和发布决定四个责任边界。
> 模型版本和离线证据由算法收口；部署包由部署工程师交付；板端测试结论由测试负责人签发；上线决定由发布负责人作出。
> 如果板端指标不达标，测试记录复现条件，相关执行人分析原因；涉及改验收指标或改发布日期，由对应决策负责人处理。”

**执行要点**：

- **先定验收口径，再做测试**：涉及硬件设置的条件也要记录，确保结果可比较。
- **交付要有接收确认**：上游提供材料，下游核对可用性并反馈缺项，避免“发到群里就算完成”。
- **范围变更要重新确认**：临时增加场景、压缩时延指标或更换硬件，都可能影响资源与期限。
- **不达标要触发明确决策**：延期、缩小范围或补充验证，需要对应授权；强制放行条件不能靠修改 RACI 绕过。

## 第四章 实际用例二：市场、销售、产品一起办客户活动

**场景说明**：市场负责组织活动，销售邀请客户，产品准备演示。活动临近，销售承诺的功能还没做完，现场物料也没人确认。以下为教学示例。

**❌ 错误示范**：

> “这是公司的重点活动，所有部门共同负责，任何问题大家及时补位。”

共同参与可以，但预算、客户承诺、演示内容和现场执行需要各自明确的负责人。

| 任务 / 交付物 | 活动负责人 | 市场执行 | 销售负责人 | 产品负责人 |
| --- | --- | --- | --- | --- |
| 在已授权额度内确认活动方案与预算 | A | R | C | C |
| 完成客户邀约与出席名单 | I | C | A/R | — |
| 确认演示内容及功能承诺边界 | I | C | C | A/R |
| 完成场地、物料与现场流程 | A | R | C | C |
| 完成会后线索分配与跟进记录 | I | C | A/R | C |

活动负责人并不因此成为所有专业事项的 A。客户邀约由销售收口，产品演示边界由产品收口，才能让整体协调与专业授权各有落点。

**✅ 高气场话术**：

> “活动由我统筹。客户名单请销售负责人在周三中午前确认；演示内容和可承诺范围请产品负责人在周二前确认；市场按确认版本准备物料。
> 客户临时提出新演示需求，销售先收集，产品评估能否提供；如果影响现场流程或预算，再由我协调调整。”

**执行要点**：

- **把承诺的权限说清楚**：邀请客户参与，不等于可以承诺新增功能。
- **给 C 设置明确反馈期限**：提出需要评估的问题、所需意见和截止时间；未回复时按事先约定升级，不能把沉默一律当批准。
- **区分专业决策和整体协调**：活动负责人协调资源与进度；超出预算授权或产品能力边界时，交给有权限的人决定。
- **会后仍有交付物**：线索分配和跟进记录单独列项，避免活动结束就无人追踪。

## 第五章 实际用例三：线上故障时谁指挥、谁修复、谁对外同步

**场景说明**：服务出现故障，运维、研发、业务和客服进入应急群。多人同时发指令，有人排查代码，有人要求立刻回滚，还有人直接向客户承诺恢复时间。以下为教学示例。

**❌ 错误示范**：

> “谁有办法谁先上，尽快恢复，客服先安抚一下客户。”

这种安排容易出现并行修改相互干扰、恢复判断口径不一致、对外信息频繁变化。

| 任务 / 决策 | 事件负责人 | 值班运维 | 研发负责人 | 业务负责人 | 客服负责人 |
| --- | --- | --- | --- | --- | --- |
| 汇总影响范围与故障时间线 | A | R | C | C | I |
| 定位原因并提出修复方案 | C | R | A/R | I | I |
| 在预授权范围内决定回滚或切流 | A | R | C | C | I |
| 执行已批准操作并验证技术恢复 | A | R | C | C | I |
| 确认业务恢复与受影响业务处理 | C | C | C | A/R | I |
| 确认并发布客户进展通知 | C | I | C | A | R |

“决定回滚或切流”中的运维 R 负责准备操作建议、影响评估和执行条件；事件负责人 A 按预案决策。需要扩大停机范围等超出授权的动作，应升级给预案指定的决策人。

**✅ 高气场话术**：

> “本次事件由我统一协调。运维先汇总影响和操作记录，研发负责定位与修复方案。涉及生产变更，按预案由对应授权人确认后执行。
> 客服按业务负责人确认的口径同步客户。恢复时间没有依据前，先说明当前影响、正在采取的措施和下一次更新时间。”

**执行要点**：

- **预先设定代理人**：A 不在线时，谁接替、何时启用、如何通知，要在值班机制中明确；同一时间保留一个生效的 A。
- **应急时先启用预案**：RACI 和授权边界应在平时准备，现场只补充缺失的人选与职责。
- **技术恢复和业务恢复分别确认**：指标恢复正常后，仍可能需要处理积压请求或客户影响。
- **复盘形成新的任务**：永久修复、监控补充、流程改进分别指定 A、R 和期限，避免停留在“加强重视”。

## 第六章 常见误区与纠偏话术

| 常见误区 | 实际后果 | 纠偏话术 / 做法 |
| --- | --- | --- |
| 同一行填两个 A | 出现分歧时无人能收口 | “这项结果需要一个最终负责人；两类独立审批请拆成两项。” |
| A 全部写老板 | 所有工作都排队等待 | “哪些决定可以授权给项目或专业负责人？请把额度和边界一起定下来。” |
| R 写“全体成员” | 每个人都以为别人会做 | “请明确各自的交付物；共同成果也需要具体的整合与提交人。” |
| 指定 A，却不给权限和资源 | 名义负责、实际无法推进 | “这项结果我可以承接，需要同时确认调配资源的权限和冲突升级渠道。” |
| 所有人都列 C | 普通工作变成层层会签 | “哪些意见会改变决策？其余人员按约定同步进展。” |
| I 被默认拉进所有会议 | 知情变成大量会议负担 | “这项向你同步纪要；涉及你的职责变化，再邀请你参与讨论。” |
| 定表后不再更新 | 人员、范围变化后职责失真 | “本次变更影响哪些交付与授权？更新责任表后请受影响人员确认。” |
| 出问题只用表追责 | 大家倾向于隐藏风险、拒绝协助 | “先恢复交付，再查目标、授权、资源、执行和沟通哪个环节失效。” |

A 对结果负责，不意味着可以忽略其他人的专业职责；R、C、I 发现重大风险，也应通过约定渠道及时反馈。责任表的价值要体现在协作效率和结果上。

## 第七章 一套可以直接复制的模板

### 1. 责任分配表

先把角色替换成项目中实际的人，再填写每一项任务。

| 编号 | 任务 / 交付物 | 角色甲 | 角色乙 | 角色丙 | 角色丁 |
| --- | --- | --- | --- | --- | --- |
| T01 | 例如：确认需求基线 | A | R | C | I |
| T02 | 例如：交付实施方案 | I | C | A/R | C |
| T03 | 例如：完成验收并形成结论 | A | C | C | R |

### 2. 配套执行卡

每项任务使用同一个编号关联执行卡，避免矩阵过宽，也方便单独跟踪。

| 字段 | 填写内容 |
| --- | --- |
| 任务编号 / 名称 | 与责任表一致 |
| A / R 姓名 | 明确到人；兼任时注明 A/R |
| 交付物及存放位置 | 文件、系统记录或可验证结果的链接 |
| 截止时间 | 明确日期与时间 |
| 验收标准及验收人 | 用哪些证据判断通过，由谁确认 |
| 前置依赖与资源 | 谁在何时提供什么；当前是否已落实 |
| 征询与通知 | C 何时反馈；I 在什么节点通过什么渠道收到信息 |
| 授权边界 | A 可以决定什么；哪些事项需要另行审批 |
| 升级条件与对象 | 如关键依赖延期、预计无法按期完成；向谁报告并请求何种决定 |
| 版本与确认记录 | 谁在何时确认；变更原因与受影响人员 |

### 3. 启动会收口话术

> “今天确认的责任表是 v1.0。每项任务的 A 和 R 已落实到人，期限与验收条件在任务卡里。
> 请各位确认自己有完成任务所需的资源和授权。存在冲突的事项现在列出，由对应负责人处理后再承诺日期。
> 后续人员、范围或期限变化时，我们更新记录并同步相关人。”

### 4. 日常练习方法

选一个正在推进、且最近发生过职责争议的事项，先列出 **5—10 个关键交付物**，不必一开始覆盖整个部门。

第一轮检查每行是否有且只有一个 A、是否至少有一个 R。第二轮让当事人确认职责、资源、期限和交接。运行一周后，对照实际发生的等待、返工和无人接收的问题，修改对应条目。

复盘时重点问三件事：**有没有无人交付的工作？有没有缺少授权的负责人？有没有该征询或通知却漏掉的人？** 用具体问题修正表格，才能让分工真正有效。
